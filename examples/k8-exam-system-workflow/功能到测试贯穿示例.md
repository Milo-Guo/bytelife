# 从提交测验到验证结果

以下是整理者的教学示例。使用 DEMO 编号避免冒充课堂正式 F/AC；接口、字段和状态是示意，不是老师完整项目源文件，也没有实际运行。

## 需求层

功能 DEMO-F01：学生提交自己的测验。

已采用课堂决定：未作答 0 分、标未作答、本期不进错题本。其他示例边界用于说明实现需要，并不表示课堂每条都已经决定。

| 验收编号 | 条件、动作与预期 |
| --- | --- |
| DEMO-AC-1 | 学生提交属于自己的进行中测验；服务端将其转为已提交，保存交卷时间 |
| DEMO-AC-2 | 含未作答题时，结果标未作答，该题 0 分，不加错题本 |
| DEMO-AC-3 | 同一测验因网络重试重复提交，不能产生第二份有效提交或重复评分任务 |
| DEMO-AC-4 | 学生 A 提交学生 B 的测验，拒绝操作且 B 的记录不改变 |
| DEMO-AC-5 | 主观评分失败时标待复核，不把未评分状态伪装成最终零分成绩 |

## 接口契约层（示意）

`POST /api/attempts/{attempt_id}/submit`

身份：使用本系统有效会话。服务端从会话确认 student_id，不能相信客户端自报的学生身份。

请求：attempt_id、客户端请求标识、按契约提交的答题内容或已保存答案版本。答案快照和提交版本如何一致，需要在真实设计中确定。

响应：attempt_id、提交状态、主观题评分状态；评分尚未结束时不要返回“最终分数已完成”。错误需区分业务状态、权限与输入问题，但避免泄露他人数据。

重复调用：使用唯一约束、条件更新或其他已确定方案实现幂等（同一逻辑操作重试不会产生重复副作用）。只在界面禁用按钮不足以实现幂等。

## 代码职责层（示意）

- routers：校验请求形状，读取身份，调用 service，转换响应。
- services：检查归属、当前状态和时间规则；决定交卷、客观评分、主观任务与事务范围。
- crud：进行具体查询与受条件保护的更新。
- models：表达表和字段映射；schemas 表达请求与响应。
- worker：处理已持久化的主观评分任务，不把 HTTP 请求线程直接当持久任务系统。

## 数据层（示意）

| 数据对象 | 支持什么行为 | 需确定的约束 |
| --- | --- | --- |
| attempts | 一次测验的归属、状态、提交时间 | 有效状态转换；同次提交的唯一性和并发保护 |
| attempt_questions | 当时的题目快照、答案、评分 | 题库改动不应无意重写历史；未作答可明确表示 |
| jobs | 主观评分排队与失败状态 | 同一逻辑评分任务不重复；领取、重试和恢复规则 |
| wrong_questions | 本期错题记录 | 遵守未作答不入错题本的已确认决定 |
| review_requests | 复核与改判 | 人工决定与迟到模型结果的冲突策略 |

这些对象名称与课堂部分表名一致，但表中说明为教学重述。不要据此推导真实字段名或复制成线上 DDL。

## 一条变更如何传下去

如果把“未作答不进错题本”改为“允许学生主动收录未作答题”，先确认是自动收录还是另一个按钮，再改需求 AC；接着检查接口参数/操作、service 分支、错题数据与唯一约束，最后调整 DEMO-TC-1 并补主动收录测试。不是每次都要加新表，但每层都应说明是否受影响。
