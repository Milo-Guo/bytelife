# 用四份提示词指挥 Agent 做自己的软件项目

对应文章第21节：https://milo-guo.github.io/bytelife/articles/k8-exam-system-workflow/#k8-21

这一节可以直接当操作手册用。K8 是老师演示软件工程流程的例子；换成库存、预约、借用、记账系统，仍可沿用“定规则 → 需求 → 架构与接口 → 数据设计 → 分功能实现与验收”的顺序。你需要替换项目事实、业务规则和技术限制，不用复刻 K8 的 47 项功能。

下面以**设备借用管理系统**演示，项目目录假设为 `D:\Projects\EquipLoan`。这是填写示例，尚未创建或开发这个系统。发送任何示例前，把路径换成自己的真实位置。

网页上每段指令框右上角有“复制”。点它后，在 agent 输入框粘贴并替换项目内容；手机上长行可在指令框内左右滑动。要离线使用，打开资料包里的 `指挥Agent操作手册.md`，内容与本节一致。

## 21.1 先分清：这四份文件各派什么活

| 顺序 | 老师附件中的文件 | 你要填的重点 | agent 应交付什么 |
| --- | --- | --- | --- |
| 00 | `00-env-setup（定规矩）.prompt` | 项目名、目录、新旧项目、已知技术限制 | 项目规则及 docs 索引 |
| 01 | `01-requirement（需求文档）.prompt` | 谁用、要做什么、不做什么、业务规则 | requirement.md、功能与 AC、待确认问题、进度台账 |
| 02a | `02a-architecture（架构设计）.prompt` | 已确认需求、技术栈、运行环境 | architecture.md；另明确要求接口契约 api-spec.md |
| 02b | `02b-database（建表DDL）.prompt` | 上游文档、数据库版本、已有数据情况、执行范围 | 数据结构说明及 SQL，按实际范围给验证记录 |

文章配套 `prompts` 目录里的文件对应这四个阶段，文件名去掉了中文括号，并修订了路径冲突等问题。**跟做推荐使用配套修订版；原始附件留一份用于对照。** 不要把两个版本同时发送，免得 agent 收到相互冲突的输出路径。

`.prompt` 是要交给 agent 阅读的文本。它不需要安装成 Skill，也不是在终端执行的脚本。里面的“你是初始化工程师”等角色说明可以保留；原项目名、学生刷题需求、个人路径、已填写的技术选项，要换成你的项目。`【选】`只保留你的答案，`【多选】`按实际填写，`【填】`和修订版里的尖括号占位都要处理；不知道的写“待确认”，不要随便填一个字母。

你在日常操作里主要做两件事：给出业务决定，检查软件实际行为。目录调查、文档写入、代码修改和测试可以让 agent 执行，工作范围已经说明后，不必每个小步骤都重新点头。

## 21.2 准备文件：两个软件打开同一个项目目录

1. 打开 Windows 资源管理器，新建自己的项目文件夹。本例为 `D:\Projects\EquipLoan`；已有项目直接用现有目录，不另起一个空项目。
2. 下载文章配套 ZIP 并解压，把里面的 `prompts` 文件夹复制到项目根目录，保留原下载包作为模板备份。
3. 打开 VS Code，点 `File → Open Folder`（文件 → 打开文件夹），选择这个项目目录。左侧应能展开 `prompts`，看到四个 `.prompt` 文件。
4. 在 Hermes 或其他能读写本地项目的 agent 工具中，打开或关联同一个目录。会话名可以叫“00 定规则”；新会话是否需要重新选目录，以所用工具为准。
5. 先让 agent 只读核对位置，确认它看到的文件与 VS Code 一致，再开始填写。

把下面这段发到 **agent 聊天输入框**，不用粘到 PowerShell 终端：

```text
我要在 D:\Projects\EquipLoan 做设备借用管理系统。
请先只读检查当前工作目录、目录下的文件和已有项目规则。
列出 prompts 文件夹里的实际文件名，并说明是否已有代码或需求文档。
如果当前目录不是这个目录，先告诉我，不要在别处创建项目。
本条只核对位置，不生成业务代码。
```

成功标志是回复列出的目录、四个提示词文件和已有文件都对得上。若 agent 读不到本机文件，先用它的“打开文件夹/关联工作区”能力选目录；仅把路径打进普通聊天窗口，并不会自动赋予文件访问能力。没有本地读写能力时，它只能提供文本，你需要手动保存产物，再把最新内容交给下一阶段。

模板里的规则文件是否会被工具自动加载，取决于工具本身。跟做时主动要求它读取实际存在的规则文件，不以文件名存在就认定规则已经生效。

## 21.3 不懂技术栈时，先让它帮你选，再填“已确定”

你可以先说业务和使用环境。例如：自己开发和维护、员工在电脑和手机浏览器使用、先本机验证、以后再部署、预算有限。再发送：

```text
我暂时不会选技术栈。请根据这个项目的规模和使用环境，
给出一个适合我维护的方案，解释前端、后端、数据存储各负责什么，
以及本机需要准备的软件、部署成本和主要限制。
先调查现有项目及本机可用环境；已有项目优先沿用现有栈。
不要立即安装或生成应用，也不要把你的建议记为我已确认。
```

看完建议后，明确回复采用哪套，把版本和限制写进 00；版本让 agent 根据实际环境或官方资料核对，不必跟着老师锁成某一年的版本。暂时无法决定的，仍标待确认，先完成不依赖它的规则和业务需求。原模板如果同时写着“技术栈已定不许改”，这句话也要调整，不能一边填待确认，一边宣称已经确定。

网页工具不一定有独立服务端或数据库；没有持久化数据需求时，不必硬套建库阶段。这里的设备借用例子需要多人共享记录，因此后面继续演示数据设计。

## 21.4 第一次正式派活：填写并发送 00

在 VS Code 打开 `prompts/00-env-setup.prompt`，把填写区改成你的信息。下面是本例的填写形状：

```text
项目名：设备借用管理系统
项目根目录：D:\Projects\EquipLoan
状态：全新项目
项目目标：员工查询设备并借用、归还，管理员维护设备和查看记录。
已确认技术约束：电脑和手机浏览器使用；先本机运行。
语言、框架、数据存储版本：填入刚才确认的结果；未决定的明确标待确认。
现有规则文件及文档：请先只读发现，现有内容比较后合并。
本次允许修改：项目规则文件、docs/README.md及本阶段文档骨架。
```

按 `Ctrl+S` 保存，回到“00 定规则”会话。发送提示词有两种方式，选择一种：

- **引用文件**：工具能读项目文件时，发下面的指令，让它读取保存后的副本。
- **粘贴全文**：在编辑器正文内 `Ctrl+A`、`Ctrl+C`，粘贴到 agent 的聊天输入框。前面加“按以下填写后的 00 提示词执行”。不要只复制文件名，也不要把四份全文一起粘进去。

```text
请读取并执行当前项目 prompts/00-env-setup.prompt。
这是我填写后的本项目任务说明。
先核对目录和已有规则，再直接完成本阶段允许的文件写入与读回核对。
本次先定规则和建立文档索引，不开始业务实现。
未确定技术项保留为待确认；面向网页的功能设计目录按 web 命名，
不要照搬 K8 的 miniapp 目录。
完成后列实际文件路径、待确认项和下一阶段输入。
```

完成后在 VS Code 打开规则文件和 `docs/README.md`，检查项目名、实际目录、运行平台和技术决定。空项目的目录只能写“拟定”，不能说已经查过某个不存在的业务模块。规则有问题就在这个会话修，不要带着错误进入 01。

## 21.5 写 01：把自己的原始想法放进模板

打开 `prompts/01-requirement.prompt`。状态填“全新”，需求路径还不存在就写“未建立”；将原始想法改成自己的业务，不需要先学会 F 或 AC。下面这段可作为本例的原始输入：

```text
我要做设备借用管理系统，先做网页，电脑和手机都能使用。
使用者是员工和管理员。
每件实物设备有唯一编号，员工能看可借设备、借用并归还，
只能看自己的借用记录。管理员能维护设备并查看全部借用记录。
本期员工借用不经过审批；设备已借出时，其他人不能再借。
归还后设备重新变为可借；借用过的设备停用后，历史记录要保留。
本期不做收费、押金、采购和维修工单。
先把“查看设备 → 借用 → 我的借用 → 归还”做通，再扩展其他功能。
账号由谁创建、一次能借几件、逾期怎样处理，我还没确定，请列问题。
```

主要角色填“员工、管理员”，可修改范围填需求、feature-list 和 docs 索引。保存后，在同一项目新建“01 需求”会话，发送：

```text
请先读项目规则和 docs/README.md，再读取并执行
prompts/01-requirement.prompt，完成本项目需求整理。
需求正文写 docs/01-requirement/requirement.md，
进度台账写同目录 feature-list.md；已有等价文件时先沿用实际位置。
把功能、验收标准、明确不做、已确认和待确认分别写清。
已明确的部分直接落盘；只把会改变业务或阻塞当前工作的缺口提给我。
当前阶段不写业务代码。不要把模板中的 K8 示例加入我的项目。
```

新开会话的目的是让任务范围清楚，仍然读取同一套项目文件。如果工具不方便切会话，也可以在原会话明确宣布进入 01，提供文件路径和范围。没必要新建第二个项目目录。

## 21.6 回答追问，然后让决定写回文件

agent 会针对缺口给 Q 编号。按它实际列出的编号回答，不照抄别的项目的 Q01/Q02 含义。下面假设它问了账号和数量限制，回复可以这样写：

```text
Q01 账号创建：采用管理员创建账号，本期不做自助注册。
Q02 同时借用上限：每名员工最多同时借 3 件。
Q03 逾期处理：本期只显示逾期状态，不计费、不发短信。
以上三项已确定，请回写需求正文、相关 AC、决策记录和进度台账。
其他未回答的问题继续保留待确认，不视为我同意默认建议。
```

不知道怎么选，就让它解释这一题各选项会改变什么；不要回复一句“全按推荐”后又忘记哪些业务已经定了。常规措辞、编号整理和引用修复可让 agent 直接完成。

这一轮完成后，打开 requirement.md，至少检查主流程及对应的失败情况。本例应该能回答：设备已借出怎么办，重复点击借用会不会多一条记录，员工能否看到别人的记录，停用是否破坏历史。不要只看功能名称够不够多。

可以再发一条检查指令：

```text
请按员工完成一次借用和归还的顺序，逐步对照需求。
列每一步对应的实际 F/AC，以及输入、结果和失败处理。
同时检查管理员的必要操作、数据归属和历史保留。
格式、引用和编号错误直接修复；涉及新业务决定的列成 Q。
报告剩余问题中哪些阻塞下一阶段，并更新 docs/README.md。
```

进入架构阶段的条件是：准备设计的范围有明确业务规则，阻塞它的决定已经解决。其他范围仍有待确认项可以保留，不必为了清空列表随便拍板。

## 21.7 发 02a：让 agent 把需求转成结构和接口

打开 `prompts/02a-architecture.prompt`，模式填“首版”；填写刚才的需求实际路径和版本、项目规则路径、已经确认的栈与运行环境。这里引用的是 **requirement.md 产物**，不能只指向当初的 01 提示词。

保存后新建“02a 架构与接口”会话，发送：

```text
请读取项目规则、docs/README.md 和最新需求正文，
再执行 prompts/02a-architecture.prompt。
请设计已确认范围的目录分工、关键流程、数据归属和事务边界，
并写出 architecture.md 与 api-spec.md。
接口要说明谁调用、输入、返回、失败原因及重复请求的处理。
重点解释两个人同时借同一件设备时，如何保证只有一个人成功。
需要新增业务决定时回到需求列问题；不要在架构里静默加功能。
本次完成设计与文档检查，暂不实现业务代码或部署服务。
```

老师的原始 02a 若没有要求完整接口文档，就把“生成 api-spec.md”这条明确加上；修订版已经包含。检查架构时，让 agent 用一次借用说明：界面怎样请求，谁检查权限，哪里判断可借，哪些更新必须一起成功，失败后用户看到什么。

检查真实文件是否有这些内容，再让它同步规则与索引。如果选型变化，先说明原因和影响，更新相关决定；不要把课堂的 worker、微信登录或模型评分当成每个系统都需要的组件。

## 21.8 发 02b：先设计数据，再按目标验证

打开 `prompts/02b-database.prompt`，填需求、架构、接口的实际路径及版本。数据库填架构已经确定的种类和版本；现有库资料没有就写“未提供”，不能写成“空库已确认”。新项目的设计模式选“首版设计”。

保存后新建“02b 数据设计”会话，发送：

```text
请读取最新需求、架构和接口，再执行 prompts/02b-database.prompt。
本次先生成数据设计和静态审阅结果，不连接现有数据库。
SQL 写 docs/02b-database/schema.sql；说明、F映射与检查记录写 schema.md。
重点核对设备唯一编号、借用归还状态、员工归属、
重复借用限制及停用后的历史保留。
字段或状态与接口不一致时，按已确认业务同步设计并记录差异。
若发现新业务问题，列出问题和影响，不能仅靠加字段代替需求确认。
完成后明确哪些已检查、哪些尚未实际运行。
```

你要看的是同一业务在需求、接口和数据中的含义是否一致。例如前面已定“每件实物一个编号”，后面就不能忽然只有一个可随意减数的“设备总库存”，却没有解释怎样定位具体借出的实物。

需要让 agent 真的验证 SQL 时，可以追加下列指令。它授权建立**新的本机隔离测试环境**，不指向你已有的业务库：

```text
本次允许你在本机新建一个仅用于 EquipLoan 的隔离测试环境，
使用架构中已确认的数据存储版本和全新测试库。
先检查所需工具是否可用、名称和端口是否冲突；可用后直接验证。
允许执行本项目建表脚本并写入虚构测试数据，禁止使用真实人员资料。
不得复用、清空或修改其他项目的库。不要在回复中展示凭据。
如果需要安装系统软件、额外付费或目标无法确认，先说明具体缺口。
记录环境、实际版本、命令、退出结果和关键约束验证。
完成后说明怎样启动、停止这个测试环境，以及它保留了哪些测试数据。
```

同一次授权范围内的排错和重试可以继续，不必每条 SQL 都问一次。正式环境已有数据时走迁移流程，不能用这段“新建测试库”的话术代替正式迁移安排。

## 21.9 四份文件用完后，怎样让 agent 真正开始开发

到 02b 主要得到规则和设计。**以下功能设计、任务卡和开发话术是整理补充，不是附件中另外存在的老师原版文件。** 你可以复制到 agent，也可以保存成自己项目的后续提示词。

先选一个可以实际走通的功能，例如员工借用一件设备。不要先要求它把全部前端、全部后端分别做完再碰运气联调。让它找出相关真实编号和依赖，做一份可执行的小范围设计：

```text
进入功能设计阶段。本轮选择“员工借用一件设备”这条流程。
先从需求找到它的实际 F/AC，读取相关架构、接口和数据设计。
识别前置条件，例如登录、已有设备数据；缺什么要列清楚。
给出页面/状态、用户操作、接口顺序、业务校验、数据变更、失败处理，
写入 docs/02c-feature-web/ 对应的功能设计文档。
接着拆出任务卡，列每张卡的目标、依赖、可改文件、对应 AC、验证方法。
任务卡保存在 docs/03-dev/tasks.md；已有任务系统时沿用实际位置。
本轮先完成设计和任务拆分，未实现的卡片保持待开发。
```

`web` 对应网页；小程序才用 `miniapp`。任务卡可以是一份 Markdown 清单，不依赖 Hermes 看板插件才能开工。卡号由当前项目实际生成，下面的填写位置要换成真实卡号。

你检查了这张卡的目标和依赖后，发实现指令。若依赖还没做，就从前置卡开始：

```text
本次实现：填写 docs/03-dev/tasks.md 中的实际卡号与标题。
请先读该卡、关联 F/AC 和设计，检查当前代码及用户已有改动。
在卡片范围内直接完成代码修改、必要的自动验证和本机运行检查，
失败就定位原因并修复，再复验；保留无关代码和已有工作。
接口、页面、真实测试数据存储要接通；仅有静态页面不算此卡完成。
测试覆盖相关业务边界，不为了凑数量写重复测试。
普通实现细节自行选择；会改变业务、技术约定或范围的决定再提给我。
沿用此前已授权的本项目隔离测试环境；未授权的环境先说明需要。
交付修改文件、实际测试结果、未完成项，以及我打开页面验收的步骤。
本轮范围为本机开发验证，Git提交、推送和正式上线按另行给出的范围执行。
```

本例有界面和共享数据，才需要检查页面、接口和数据能否走通。做命令行工具时，把交付改成真实命令、输入文件和输出结果，不硬套网页三层。

## 21.10 你怎样验收：让它告诉你点哪里、看到什么

让 agent 从实际项目文件中找启动命令，不能无论什么栈都套 `npm run dev`。发下面这段，就能把“完成了”变成你能操作的交付：

```text
请根据当前项目真实脚本和配置，给我本轮功能的验收操作。
写进 README 或现有运行文档：
1. 打开哪个软件、哪个项目目录。
2. 首次依赖准备、正常启动、停止分别用什么真实命令。
3. 启动成功的输出和实际访问地址。
4. 测试账号或测试数据怎样准备，不公开真实凭据。
5. 按什么顺序点击，每一步应看到什么。
6. 常见失败在哪看日志，哪些步骤已经由你实测。
不能运行的部分写清原因，不能用“应该能跑”代替结果。
```

设备借用的人工验收可以这样走：管理员添加一件测试设备，员工 A 借用后看自己的记录；员工 B 再尝试借同一件设备，应得到不可借提示；A 归还后，设备恢复可借，旧记录仍在。并发请求和重复提交让 agent 用自动化验证，你负责核对界面和业务是否符合预期。这些是待执行的验收步骤，不是本教程已经测过该示例系统。

报错时在同一开发会话发“执行了什么、完整错误、预期行为”，可以直接使用：

```text
我在（实际页面/命令）执行（动作）时出现以下错误：
粘贴错误原文或提供截图，并去掉其中的密码和密钥。
预期是：填写我应该看到的结果。
请定位原因，在当前卡片范围内修复，复测原场景及直接受影响的行为。
说明修了哪里和实际验证结果，不重新初始化项目。
```

功能通过后，要求它更新 feature-list 和任务卡，分别记录“已实现、已验证、未验证”，再开始下一张卡。你后来准备发布时，另说明仓库、分支、运行环境和允许的发布动作；有数据库迁移就先准备迁移、备份和回滚安排。

## 21.11 中断、换会话、加需求时，继续读文件

换会话时复制下面这段，括号内容按实际填写。它比“继续昨天的”更容易让新会话接上：

```text
继续项目（真实根目录），当前阶段为（阶段名）。
先读实际存在的项目规则、docs/README.md、当前任务卡和所需上游文档，
再核对磁盘与Git状态，确认上一轮实际做到哪里。
当前任务：（实际卡号/问题）；本轮允许范围：（具体范围）。
其他相关会话已停止写入；保留用户尚未提交的修改。
从未完成步骤继续，在已授权范围内完成并验证，不重跑整个初始化。
资料冲突时列证据，缺少业务决定时指出它影响哪一步。
```

想新增审批、短信提醒等能力时，先停止当前范围的并发写入，用配套 `增量变更交接模板.md` 说明变化。让需求阶段补 F/AC 与决定，再同步受影响的架构、接口、数据和任务卡。原有编号和已通过的工作保留；只改了 prompt 文件，还要重新发送本次变更，不能期待成品自动更新。

同一会话中断也先检查文件和任务结果，取消一次生成不等于撤销已经写入的内容。已有项目则从一开始就选择“二开/增量”，让 agent 先调查，不用这套操作把原项目重新覆盖一遍。

## 21.12 每次派活都写这几项

如果记不住前面的长指令，可以用下面的短格式。需要完整阶段约束时，再引用那一份填写好的 `.prompt`：

```text
在哪做：项目根目录。
按什么做：本阶段prompt、实际规则、上游产物路径和版本。
这次做什么：阶段范围或具体任务卡。
交出什么：实际文件、可运行行为、验证证据。
完成后怎么查：我打开哪个文件或页面，执行什么，预期看到什么。
什么需要我决定：会改变业务/成本/已有数据的未决事项。
```

你可以从 **21.2 建目录与放文件**开始照做：发 00 并检查规则，发 01 并回答业务问题，发 02a 得到结构与接口，发 02b 得到数据设计，再按 21.9 至 21.10 完成一条能运行、能验收的功能。下一轮接着推进任务卡，项目事实始终写在项目文件里。
