# 需求与架构交接审阅清单

这是人工检查清单，不是自动化测试结果。每次只对照当前实际文件打勾，不确定的保留未完成。

## 需求

- [ ] 项目名称、文件路径与已有规则一致，AI 列出了实际读取的文件。
- [ ] 背景写清谁在什么场景遇到什么问题，而不只是“做一个系统”。
- [ ] 每一类用户能查看和修改哪些数据都说清楚；菜单显示与数据权限没有混用。
- [ ] AI 提议的功能没有未经确认混入本期范围。
- [ ] 本期明确不做的事情有 NX 编号。
- [ ] 每个模块有 M 编号，每个功能有唯一 F 编号。
- [ ] 每个 F 至少映射一个 AC，没有找不到功能的孤立 AC。
- [ ] AC 能按前提、动作、结果判定，包含失败或边界情况。
- [ ] “保存成功”包含真实保存与重新读取的证据，没有只看成功提示。
- [ ] 统一了术语、时间范围、金额单位、排序和空状态。
- [ ] 初始化选项、测试数据、Mock 分开说明，测试不会污染真实数据。
- [ ] 预算、规模、使用设备、离线和恢复要求已决定或明确待定。
- [ ] 模块、功能和 AC 数量统计与正文一致。
- [ ] 真实需求由提出者逐条审阅；没有把示例或机器自查当成人工确认。

## 架构

- [ ] 新会话引用了已确认需求的真实文件及版本，未假定继承了旧聊天。
- [ ] 既有规则未被模板覆盖；未知技术栈没有偷偷选定。
- [ ] 每个部分的责任、边界和依赖方向明确，符合项目规模。
- [ ] schemas、ORM models 和业务模块的含义没有混淆。
- [ ] F → 负责部分 → AC → 验证方式可追踪，范围外功能没有回流。
- [ ] 前端提示、服务端校验（如有）和数据约束各有作用，权限在可信一侧执行。
- [ ] 估算写清人数、频率和峰值假设，不把日活、PV、UV、QPS、并发混作一项。
- [ ] 未用“多个进程必然倍增性能”替代真实压测。
- [ ] 存储失败、持久化限制、备份和恢复能力如实说明。
- [ ] 未实现、未测试、未部署均如实标注；文档完成没有被写成软件完成。
