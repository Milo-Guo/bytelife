# 把这套流程用到自己的项目

本文以设备借用管理系统为例，讲从已有设计到单卡开发、独立验收和交付的操作顺序。例子不包含可运行系统；你要把名称、路径、编号和命令换成当前项目的真实值。

## 第1步：打开项目，保护已有工作

打开 VS Code，选择 `File → Open Folder`（文件→打开文件夹），选项目根目录。在 `Terminal → New Terminal`（终端→新建终端）确认路径。已有Git仓库可运行：

```text
git status --short --branch
git log -1 --oneline
```

成功结果是看到实际分支、提交和改动清单，不要求工作区必须干净。若提示“not a git repository”，先核对目录和版本管理方式，不要删除文件、重置或自动初始化来掩盖问题。

给 Agent 的第一条话术：

```text
这是我的项目：〈绝对路径〉。先只读检查，不开始实现。
读取适用规则、项目结构和现有运行说明，列出已有改动，说明怎样保留。
告诉我需求、架构、接口、数据库、各端功能设计、测试台账分别在哪。
找不到就标待确认，不新建一套重复文档，不猜技术栈或启动命令。
按《01-开发前检查表》列出可以开工和暂时不能开工的部分。
```

## 第2步：准备规则和三份流程文件

在项目已有的提示词目录中放置本包的03、04、05文件。已有同职责文件时先比较和合并，不覆盖。把02中的适用条目追加到现有规则，明确引用真实路径。

```text
请先比较现有规则〈路径〉与《02-开发流程规则补充》。
保留原有技术栈、目录、用户权限和编码规范，只合并缺少的开发流程。
列出冲突和处理理由；不要全量替换原文件。
规则中明确引用：开发〈实际路径〉、验收〈实际路径〉、冻结〈实际路径〉。
完成后回报哪些条款新增、哪些保留、哪些还需确认。
```

检查点：规则文件仍保留原项目内容；三份提示词能从规则找到；没有两处互相矛盾的提交/测试约定。`.prompt`不会自动执行，每次派任务仍须让Agent读取它。

## 第3步：补文档缺口，再限定第一批

比如需求写了“借用申请”，功能设计还必须交代谁可申请、从哪里操作、日期与库存怎样判断、成功后数据如何变、异常文案和接口是什么。任何一项未确认，先补资料。

补API文档的话术：

```text
我先前已有架构〈路径〉和功能设计〈路径〉，现在发现接口契约没有完整落地。
请以这些文件和现有代码为依据，核对差异，补到〈指定实际路径〉。
保留真实API编号、HTTP方法、完整路径、鉴权、请求、成功与失败响应。
不发明字段或错误码；冲突列成待确认。
同步架构、功能设计和目录索引对接口文件的引用，避免生成后没人使用。
本轮只补设计和引用，不实施业务功能。
```

第一批不要写“把整个系统做完”。可以先做环境/骨架，也可以选已满足依赖的单一功能。若选骨架，逐项定义“跑通”的观察标准，例如服务健康检查、页面加载、测试发现成功、测试库迁移；不要把完整登录业务悄悄并入“空骨架”。

## 第4步：确认角色和工具实际存在

```text
检查当前可用的项目经理、后端、前端/客户端、独立审查角色。
回报真实配置名和调用方法，不把PM当成通用命令，不虚构CLI。
没有某角色或看板插件时，说明缺口；先用Markdown任务表，由主Agent按职责顺序执行即可。
本批开发并发上限是〈数量〉。同一共享文件和迁移文件由一个负责人写。
```

如果用看板，先确认项目对应的板名，避免读到旧项目或他人截图。截图里显示“完成”，还要确认对应的是拆卡还是开发、哪个版本以及有没有验收证据。

## 第5步：只让PM拆卡，不让它顺手实现

```text
本批目标：〈具体结果〉。
本批范围：〈已确认F/M/AC〉；暂不处理：〈范围〉。
拆分粒度：〈只保留一个选项〉。
读取〈规则〉和〈设计文档〉，只输出任务卡计划到〈路径〉。
每卡列目标、输入、3至5条具体AC、允许修改文件、依赖、开发角色、审查角色和证据要求。
接口按HTTP方法+完整路径引用，字段沿用数据库设计。
只做拆解，不写业务代码，不派单，不递归启动子任务。
输出卡片依赖表，并说明哪些卡可并行、哪些共享文件必须串行。
```

检查点：一张卡可以独立验收；依赖没有环；接口、表字段与AC均有来源；没有把整套系统塞进一张卡；没有保留互斥的三种粒度选项。

可用任务表：

| 卡号 | 目标 | 依赖 | 负责人 | 审查者 | 状态 | 证据/阻塞 |
| --- | --- | --- | --- | --- | --- | --- |
| 〈卡号〉 | 〈目标〉 | 〈卡号或无〉 | 〈实际角色〉 | 〈实际角色〉 | 待办 | 〈说明〉 |

## 第6步：准备测试环境与唯一迁移入口

使用检查表里的实际配置。测试账号不应有修改生产数据的权限，测试重置逻辑要确认指向隔离库。

```text
开工前先确认测试服务、测试数据库和专用账号的目标，不打印凭据。
列出本卡会创建、修改或清理哪些测试数据；范围超出授权则停止该操作并报告。
数据库结构沿用〈迁移工具/已确认流程〉作为唯一执行入口。
如另导出SQL，标明版本和用途，禁止在已经迁移的同一库上重复执行。
环境尚不具备时，不用生产库、不临时改成假数据通过验收。
```

如果端口被占用，先查哪个服务占用、是否属于本项目，再选可用端口并同步前后端、代理和运行说明。按 `06-文档变更核对表` 记录。课堂的8010/8030是现场环境，不是所有项目的固定端口。

## 第7步：给开发者发一张填好的TDD卡

复制03文件，填完项目常量和本卡输入。比如“设备借用日期校验”卡，要先有真实需求：哪些日期格式有效、空值怎么办、开始日晚于结束日怎么报错、失败是否禁止写入。没有定义不能让Agent自己猜。

```text
只执行任务卡〈卡号/路径〉，先读取〈03提示词实际路径〉。
确认前置依赖与环境后，跑既有测试基线。
再为本卡新行为写测试并实际运行，保存Red证据；确认失败是预期行为缺失而非环境问题。
然后最小实现，重跑同一测试和受影响回归，保存Green证据。
不得为通过而改期望值、删断言、加skip或硬编码返回。
当前Git授权是〈实际范围〉，未经授权不提交或推送。
最后更新台账，标为待审查，不自行宣布整个模块已完成。
```

检查Red：是否真的发现并运行了用例；失败是否对应新增行为。检查Green：是否同一组断言；还有哪些旧测试受影响；是否记录版本、命令、退出码。

若已使用pytest，可在项目确认过的环境中运行 `python -m pytest 〈真实测试路径〉 -q`。这是示意，先替换路径；其他语言继续使用自己的现有测试命令。

## 第8步：看进度时先分清状态

| 看见什么 | 能证明什么 | 下一步 |
| --- | --- | --- |
| 卡已创建 | 计划进入台账 | 查依赖和允许放行范围 |
| PM卡完成 | 拆解产物已交付 | 核对卡内容后才派开发 |
| 正在运行 | 某个命令/Agent仍工作 | 看最新日志，避免重复派同一任务 |
| blocked/initial_status | 可能是初始暂存或等待依赖 | 读原因，按放行规则处理，不能盲目重试 |
| 开发自报完成 | 实现者认为完成 | 查测试证据，派独立审查 |
| REVIEW通过 | 报告范围内已验收 | 检查未覆盖项，再准备该批冻结 |

卡卡住时的话术：

```text
只诊断〈卡号〉，先不要重跑或再建一张重复卡。
区分等待依赖、初始未放行、需要确认、环境错误、配额/限流、实现失败、验收失败。
给出最近真实日志和状态，指出第一处可以验证的原因。
检查是否已有后台任务仍在运行；若要重启工具，先说明会影响哪些任务和如何恢复。
按已授权范围做最小修复，恢复后核对原卡，保留失败与重试记录。
```

429、Gateway断开和测试失败不是同一种问题。其他HTTP错误也要按真实日志判断。不要用“模型不行”代替排查。

## 第9步：把模块交给独立验收

所有前置开发卡完成后，派04提示词。审查者从需求出发，不能只接受开发者的摘要。

```text
验收〈模块/批次〉，读取〈04提示词〉、〈需求/契约〉和〈用例台账〉。
当前版本是〈真实版本〉，测试环境是〈已确认环境〉。
先查产品运行路径中的假数据线索，再核对前端调用与后端路由的HTTP方法+完整路径。
最后真实启动系统，按AC走成功和失败分支，在Network里核对请求、响应及测试数据变化。
本轮只交报告，不修代码；每项写通过/失败/未验证和证据。
缺环境时明确缺什么，不能用代码静态推断代替运行结果。
```

使用浏览器时，打开测试页面，F12→Network→Fetch/XHR，执行一次动作，点请求看Headers、Payload、Response。页面弹“成功”只是一个观察点，还要检查业务返回、数据库和页面是否一致。

## 第10步：按发现开修复卡，再复验

```text
按验收报告〈路径〉中的问题〈编号〉修复，限制范围为〈文件/行为〉。
先证明问题能复现，补上针对缺陷的测试，再最小修复并重跑受影响回归。
若发现需求、接口或字段口径矛盾，先按文档变更核对表处理，不擅自降低AC。
完成后由独立审查者复验这些问题，并给出本批最终状态。
```

修完一处就扩大成整库重写，容易破坏已有工作。确认真正需要结构性调整时，另列任务并说明风险。

## 第11步：冻结或诚实交接未完成工作

已验收的批次用05的“发布准备”模式，记录运行、迁移、检查和回退。没有发布授权就只准备可审查材料；已经明确授权时按范围完成并核对真实上线结果。

```text
使用〈05提示词〉整理〈本批〉的发布准备。
只以〈独立验收报告〉和真实版本为依据，列出范围、运行步骤、配置项名称、迁移入口、回退及未验证项。
当前授权：〈具体范围〉。权限之外的操作不自动执行。
给我可检查的交付目录与验证证据，再说明剩下的最小动作。
```

如果还没跑完，使用“未完成交接”模式：

```text
现在整理未完成交接，不把任务标为完成。
记录当前版本和要保留的改动，逐卡列已验证、待审查、待依赖、待放行和失败状态。
列出仍运行的任务及最后观测时间；不要重复创建或重启它们。
指出下次先打开哪个目录、读哪个文件、检查哪个状态，再做哪一个最小动作。
```

## 已有项目二开怎么套

先读源码和既有文档，再跑原测试建立基线。特征测试记录已有行为，可以从一开始就通过；别故意制造红灯。新需求、修复和有意改变的行为另写有鉴别力的测试，再进入本手册第7步。

补文档不是宣布旧系统正确。源码、需求和文档不一致时要把事实列出来，确认究竟改实现还是改文档。保留原编号、兼容约束和数据迁移边界。

## 最后自己核对六件事

- 能从每条AC找到TC、实现和实际证据。
- 每条命令都注明工作目录和真实运行结果。
- 测试没有连到生产数据，秘密没有进入材料。
- 前后端按方法+路径和数据变化验证过。
- 审查者确实复验，修复没有悄悄改低标准。
- 尚未完成的状态写清楚，接手者知道从哪里继续。
