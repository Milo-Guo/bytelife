# 规则验收清单

整理者补充。建议复制一份记录到目标项目文档中，检查完成后填日期与证据；不要预先把复选框全部勾上。

## 1. 文件拿对了吗

- [ ] 规则放在目标项目的正确位置，不停留在压缩包或示例包的 starter 子目录。
- [ ] 名称是工具支持的准确名称，例如 AGENTS.md 的 S 没有漏掉。
- [ ] 打开后是可读的 Markdown，不是以 `<!DOCTYPE html>` 开头的 GitHub 网页。
- [ ] CLAUDE.md 中需要执行的导入行在代码围栏和行内代码之外；该工具确实支持这种语法。
- [ ] 原有同名规则已经对照，未被整份覆盖。

## 2. 内容能核对吗

- [ ] 项目名、入口、函数、目录和依赖都有依据，未知的仍标为“未确认”。
- [ ] 新项目候选结构标为“拟定”，没有冒充扫描结果。
- [ ] 命令写清执行目录和前提，没有把示例命令当成实测记录。
- [ ] 规则说明了具体职责和验收标准，不只写“保持规范”“全部完成”。
- [ ] 保留现有技术栈，不为套模板改成指定框架、目录或微服务。
- [ ] 演示数据和 mock 有标识；真实保存和接口效果需要另外验证。
- [ ] 没有真实密钥、私聊、个人账号会话或不必要的私人路径。

## 3. 工具读到了吗

- [ ] 在工具文档或会话加载信息中检查了规则来源与范围。
- [ ] 已核对文件名、目录、版本、设置及导入方式，而不是只问“你读了吗”。
- [ ] 只支持手动附加材料的工具，已在本轮明确附上需要的规则。
- [ ] 没把普通文件名当作已安装的 `/命令`，也没把 MCP 当作规则文件加载器。

## 4. 做一个小任务检验

选择可撤销的小修改，例如修正一段说明。先记录目标，再观察 AI 是否先核对真实文件、只修改相关范围、诚实说明未运行的检查。

- [ ] 有 Git 的项目先检查了工作区状态；非 Git 项目没有擅自初始化仓库。
- [ ] 实际修改与本轮授权一致，未顺手装包、改业务、改配置或公开发布。
- [ ] 差异中保留了原有工作，没有无关格式化或目录搬动。
- [ ] 验证报告与实际执行相符；失败和未验证项没有被写成通过。
- [ ] 把此次有价值的问题回写到恰当文档，而不是无限加长全部规则。
