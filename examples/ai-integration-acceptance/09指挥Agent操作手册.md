# 09 指挥 Agent 操作手册

这是课堂重写的协调手册，不对应某个固定插件API。项目负责人先确定实际工具、角色和命令，再让指挥 Agent 使用。可放在项目既有流程文档目录；不覆盖原有操作规范。

## 一、开工前建立事实

读取01号检查表、适用规则、设计和现有任务。确认谁正在做什么、哪些文件已改、哪些服务和测试仍在运行。查询 PM 工具中的真实角色名称与状态字段；工具不可用时用项目已有看板或任务表，不编造调用。

留一张批次表：

| 批次/卡ID | 模块和目标 | 负责角色 | 前置依赖 | 允许路径 | 环境/共享资源 | 状态 | 证据 |

## 二、先补设计缺口，再安排执行

用03号模板查筛选字段、控件、列表和端覆盖。不要仅依据功能名称派卡：设备借用里的“归还”可能同时涉及管理员确认、借用人状态、库存及异常赔偿，实际范围应由业务设计决定。

设计文档修订只能证明设计更完整。需要接口、表结构或基础设施变更时，将对应依赖明确拆卡；依赖未完成的下游记blocked，不让worker自行补猜。

## 三、控制并发的实际影响

课堂示例的每批5个功能、2并发不是固定最优值。看文件重叠和共享资源决定容量。两个worker即使在不同worktree，也可能共用数据库、端口、缓存、队列、对象存储和浏览器状态。

遇到测试会TRUNCATE/重建夹具数据时，必须确认专用测试库和占用情况；未隔离则串行执行。测试突然大量失败，先排查环境互踩，不直接改断言“修绿”。

同一工作树的多会话修改即使不产生Git冲突，也可能混入同一提交。出现归属不清，按07号流程协调暂停；保留用户工作和未提交半成品。没有明确提交授权，不自动提交或推送，更不能使用 `git add .` 把所有变更混在一起。

## 四、每张卡闭环

派卡时写清输入、范围、依赖、预期输出和完成证据。worker回报后核对实际文件与结果；代码写完不直接等于验收通过。

- 开发完成：对应产物存在，并提交本卡检查结果供审阅。
- 待验收：实际运行环境与前置依赖已齐，可以按案例验证。
- blocked：明确缺少的依赖、负责方和解除条件。
- 暂停中/已暂停：同时核对父卡、子卡、worker和运行进程；状态变更不是进程停止证据。
- 完成：当前基线的验收条目有证据，缺陷与跳过项已按规则处理。

按实际PM状态做映射，不强行改工具配置。区分“任务执行完了”和“用户目标完成了”。

## 五、用真实服务验收

执行05号模板，验证入口→页面→接口→业务逻辑→数据→结果反馈。数据库账户不是应用测试账户；先确认应用登录身份和权限。

管理端能登录后，仍需点击当前范围的菜单并执行增改查等操作。页面只读、按钮没接线、后端漏字段和详情返回错误，都可能在“登录成功”之后才暴露。

分别记录各测试套件的passed、failed、skipped、blocked，不把某次串行复测通过推广为整个项目在所有版本都通过。验收结论绑定具体范围、版本和环境。

## 六、发现问题后回写流程

先用06号缺陷卡修真实问题，再把可重复的经验回写到相应规则：

- 筛选遗漏→功能设计审查项；
- 端没接线→覆盖矩阵与派卡完成条件；
- 事务/契约遗漏→分层规则及相关测试；
- 测试库互踩→环境隔离/串行门槛；
- 多会话改动混入→暂停、归属和恢复流程；
- 来源与图片不足→数据导入前置评估。

不要把一次特例升级成不分场景的全局禁令。每轮保留修订原因，方便以后判断规则是否仍适用。

## 七、向负责人交付什么

交付一份可打开的报告，包含：本阶段目标、当前基线、任务与缺陷状态、实际改动路径、测试/验收结果、脱敏证据、仍阻塞的依赖、下一批能否开始。

认证状态、口令、Cookie、令牌和含秘密的种子数据留在指定非公开位置，不混入公开截图、资料包或仓库。文件未更新、测试没运行、worker未停止时如实说明，不能用“已安排”代替结果。
