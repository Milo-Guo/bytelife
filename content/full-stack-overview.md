## 01 一个商品网站到底要做什么

### 1.1 先给自己一个能想象的目标

假设一家小店想做一个网站：店员录入商品，顾客查看商品。

先只做五件事：

1. 店员填写商品名称、价格和库存。
2. 点击“保存”，系统记住这件商品。
3. 店员关闭页面、重新打开，商品仍然存在。
4. 顾客只能看已上架的商品，不能修改价格。
5. 别人通过一个地址就能使用网站。

这五件事已经包含了一个小型全栈项目的主要工作。界面好看只是其中一部分，数据保存、权限和持续运行也需要有人负责。

### 1.2 四个角色先分清

**前端：用户操作的界面。** 例如名称输入框、价格输入框、保存按钮、商品列表。前端负责把数据展示给人，并收集人的操作。

**后端：处理业务规则的程序。** 例如检查价格能否为负、谁有权修改商品、怎样保存记录。这里的“业务”就是这个网站要遵守的具体规则。

**数据库：保存和查询记录的软件。** 例如保存商品编号、名称、价格和库存。页面关闭后数据还在，需要真正写入可长期保存的位置。

**运行环境：让上述程序能够执行的条件。** 例如操作系统、对应语言的运行工具、配置与网络。它们解决的是“程序放在哪、怎样启动、怎样持续工作”。

先记住这条主线：

人先操作页面，页面把要求发给后端。后端检查业务规则并读取或修改数据库，再把结果返回页面，页面据此更新显示。

**自检：** 保存成功的提示出现了，是否一定代表商品已经写入数据库？不一定。提示可能只是前端写死的文字。需要再次查询，必要时检查数据库，才能验证保存。

### 1.3 “全栈”与“技术栈”

**全栈 Full Stack** 在这里指能理解并完成界面、服务端、数据和交付之间的协作。一个人可以在某些方向较强，不需要对所有软件都达到专家水平。

**技术栈 Tech Stack** 是这个项目选择使用的一组技术。例如页面用一种工具，后端选一种语言与框架，数据选一种数据库，再选择运行和部署方式。

所以，“会做全栈”不能通过“电脑上安装了多少个软件”判断。更实际的判断是：能否把一个功能做通，知道代码和数据分别在哪里，出错时有办法检查。

### 1.4 课件的五层怎样放回这条主线

| 课件层级 | 在小店网站里是什么 | 主要关心什么 |
| --- | --- | --- |
| 用户层 USER | 顾客和店员使用的浏览器、App、小程序 | 从什么入口使用 |
| 接入层 EDGE | 域名、HTTPS、请求转发服务 | 怎样找到系统并进入正确入口 |
| 应用层 APP | 商品页面和处理商品的后端程序 | 界面与业务怎样实现 |
| 数据层 DATA | 商品记录、图片文件、搜索索引等 | 不同信息怎样保存和读取 |
| 运行层 RUNTIME | 操作系统、容器、服务管理 | 程序依靠什么运行 |

这五层是一种理解分工的地图。运行层承载服务，不是请求查询数据库之后还要再“走一遍操作系统”才能完成。

## 02 代码怎样变成运行的软件

### 2.1 源代码、项目、文件夹与配置

**源代码** 是人和 AI 编写的程序文本。代码保存在文件里，文件又放在文件夹里。文件夹在开发中也叫“目录”。

**项目** 通常是一组相关文件的集合，包括代码、图片、说明、依赖清单和配置。

下面只是目录示意，不是要求照着安装或运行的现成项目：

一个项目可能把页面代码放在 `frontend/`，把业务处理代码放在 `backend/`，用 `README.md` 写运行说明，另有连接地址、端口和依赖配置。具体目录以项目为准。

**配置** 决定程序在当前环境怎样工作。例如连接哪一个数据库、监听哪个端口。相同代码可以因为配置不同，连接不同的数据。

看到一个仓库里有很多文件，先找项目说明，再识别前端和后端入口。不要看到名字像配置的文件就随意修改。

### 2.2 语言、框架、库、工具、协议与平台

这些英文名字之所以难记，部分原因是它们并不属于同一种东西。

| 类别 | 含义 | 例子与使用方式 |
| --- | --- | --- |
| 编程语言 | 表达程序逻辑的语言 | 用 Java、Python、JavaScript、Go 写代码 |
| 框架 Framework | 帮你组织某类程序，并提供常用机制 | 按 Vue、Spring Boot、FastAPI 的方式写页面或接口 |
| 库 Library | 可以在代码里调用的一组现成能力 | 用 axios 发送请求，用 FAISS 做相似度检索 |
| 开发工具 | 帮助编写、检查、构建程序的软件 | 编辑器、Git、构建工具 |
| 独立服务 | 启动后等待其他程序来访问的程序 | 后端服务、数据库服务、Redis 服务 |
| 协议 Protocol | 双方通信时遵守的约定 | HTTP、FTP、MCP |
| 平台 | 提供一组托管或协作功能的产品 | GitHub、云平台、阿里云云效 |

这些类别有时存在交叉，例如框架也通过软件包安装。目的不是死记分类，而是判断： **这个东西是我用来写代码的、被代码调用的，还是需要单独启动的？**

### 2.3 依赖、软件包与“安装”

如果代码调用了别人写的能力，就需要让项目能找到那部分代码，这叫使用 **依赖** 。可安装的代码及说明等通常组织成 **软件包 Package** 。

有的安装会得到可以点击打开的软件，例如 Docker Desktop；有的安装只是给项目增加一组文件，例如 Vue 或 axios。不能期待所有工具装好以后都在桌面出现图标。

**包管理器** 帮助下载和管理依赖。为补齐安装过程，额外认识几个名字：

- **npm：** JavaScript 项目常用的包管理与脚本执行工具，通常随 Node.js 提供。
- **pip：** Python 常用的软件包安装工具。
- **Maven / Gradle：** Java 常见的依赖与构建工具。

这些是理解工程时的补充知识，不是这节课已经逐一教过的操作。不同项目应按自己的说明使用，不能把不同项目的安装命令随意混用。

### 2.4 编辑器、终端、CMD、PowerShell 与命令行

**编辑器 / IDE** 是读写代码的工作场所。例如 VS Code 是编辑器，某些 IDE 还集成编译、调试等能力。

**终端** 是与命令行程序交互的窗口。Windows 上常见的命令解释环境有 CMD、PowerShell。输入命令以后，由相应环境解释并运行。

命令通常在某个 **当前目录** 下执行。相同命令在不同目录运行，可能找到不同配置，或提示找不到文件。

“打开终端”以后，应先确认自己在哪个项目目录，再照项目说明执行。命令结束没有报错，也要观察是否真的得到预期结果。

### 2.5 运行环境、编译与进程

**运行环境 Runtime** 让程序能够执行。Python 代码需要相应解释器与依赖；JavaScript 可以在浏览器或 Node.js 中执行，二者提供的能力并不完全相同。

**编译 Compile** 把代码转换为另一种程序表示或可执行产物。不同语言方式不同，后面会分别解释 Java 和 Go。

**进程 Process** 可以先理解成一个正在运行的程序实例。安装是准备文件，启动才会产生运行中的进程。一个软件也可能有多个进程。

**服务 Service** 强调持续为其他程序或用户提供能力。例如后端启动后等待请求，数据库启动后等待连接。服务不一定有可以点击的业务界面。

### 2.6 本地、局域网、远程与生产环境

| 词 | 具体意思 |
| --- | --- |
| 本地 Local | 当前使用的这台电脑或设备 |
| 局域网 LAN | 家里、办公室等同一局部网络中的设备 |
| 远程 Remote | 通过网络访问的另一台机器或系统 |
| 云端 | 由云服务商等提供的远程计算或存储资源 |
| 开发环境 Development | 方便修改、调试和尝试的环境 |
| 测试环境 Test | 验证功能与修改效果的环境 |
| 生产环境 Production | 正式给用户提供服务的环境 |

生产环境不是某一种特殊语言或操作系统。它描述的是用途：真实用户在这里使用，真实数据在这里产生。

课程强调这些基础的原因是：AI 可以生成代码，但若不知道它改的是哪个目录、启动的是哪个服务、连接的是哪份数据，验证就容易出错。

## 03 用户看见的页面怎样做出来

本章按“先有页面，再需要更方便的组织方式”解释。课堂介绍的 Vue 周边工具，都能放在这个过程里理解。

### 3.1 浏览器、UI、GUI、Web UI

Chrome、Edge 等 **浏览器 Browser** 可以获取网页文件、解释网页内容，显示界面并运行网页中的 JavaScript。

**UI（用户界面）** 是用户与系统交互的部分。 **GUI（图形用户界面）** 强调按钮、窗口、图标等图形形式。 **Web UI** 则是通过网页使用的界面。

一个商品列表可以出现在网页中，也可以出现在独立 App 里。只看界面截图，通常不能确定全部技术，也不能获得服务端源码和数据库。前端可见的内容与服务器内部的实现应分开理解。

### 3.2 HTML、CSS、JavaScript：先理解页面的三个基础

**HTML** 用来组织内容：标题、图片、输入框、按钮、表格。例如“保存”按钮和“价格”输入框在 HTML 中有对应元素。

**CSS** 用来控制显示方式：颜色、间距、宽度、字体、布局。按钮靠左还是靠右，手机上列表怎样排列，主要涉及这部分。

**JavaScript，简称 JS** 用来编写交互逻辑：点击按钮后收集输入、发送请求、根据结果更新界面。

```text
HTML：页面上有哪些内容
CSS：这些内容怎样排列和显示
JavaScript：发生操作后怎样处理
```

课堂里把浏览器开发者工具打开，查看元素与右侧样式，就是在观察前两部分。Java 与 JavaScript 是两门不同语言，名字相似不代表相同。

**H5** 在很多中文工作场景中是对 HTML5 或移动网页的口语称呼。 **CSS3** 是历史上对 CSS 新一代能力的常见称呼。它们都不是一个需要单独安装、打开的“页面制作软件”。

### 3.3 响应式布局与数据响应，是两件事

**响应式布局 Responsive Design：** 页面根据屏幕或窗口宽度调整排版。例如电脑上商品一行四列，手机上一行一列。课程缩小浏览器窗口的演示属于这种变化。[MDN 响应式设计说明](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/CSS_layout/Responsive_Design)

**数据响应 / 响应性 Reactivity：** 程序中的状态改变后，相关界面更新。例如购物车数量由 1 变成 2，页面上的数量随之变成 2。

两者都可能被简称“响应式”，要根据上下文判断。屏幕变窄，不表示数据库记录发生变化；页面数据变化，也不一定与屏幕宽度有关。

### 3.4 Vue 3：页面复杂以后，怎样组织和更新

**它是什么：** 一个构建用户界面的 JavaScript 框架。

**解决什么问题：** 当页面内容很多，手动管理界面与数据的关系会变复杂。Vue 帮助描述“数据是什么时，界面应该怎样显示”。

**在例子里：** 商品列表是一个组件，新增商品表单是另一个组件。保存后更新商品数据，相关列表就能按代码约定更新。

**组件 Component** 是可组合、可复用的一块界面与相关逻辑。一个普通 HTML 元素与一个封装好的 Vue 组件并非完全相同的概念，组件内部可以包含很多元素。

**数据绑定** 是在数据和界面之间建立关系。例如表单中填写的商品名称，与程序里的某个变量关联起来。

Vue 不负责代替数据库永久保存商品。它帮助组织前端，保存仍然需要相应的数据流程。[Vue 官方入门](https://vuejs.org/guide/introduction.html)

### 3.5 Node.js、npm 与 Vite：开发时为什么还有这些东西

**Node.js：** 在浏览器外执行 JavaScript 的运行环境。Vue 项目开发时，经常用它执行开发工具。Node.js 也可以用来写后端，但“项目装了 Node.js”不表示这个项目后端一定用 Node.js。[Node.js 官方说明](https://nodejs.org/en/about)

**npm：** 帮助安装项目依赖，并按项目配置执行脚本。例如项目需要 Vue、axios 等依赖，可由包管理器准备。

**Vite：** 前端开发与构建工具。开发时提供方便预览和更新的服务；发布前，按配置把代码整理成供目标环境使用的文件。[Vite 官方说明](https://vite.dev/guide/)

把三者放在一起：

Node.js 运行开发工具，npm 根据项目清单安装依赖和执行脚本，Vite 提供开发预览或生成发布文件。浏览器最后取得页面文件并执行前端代码。

常见的 `package.json` 文件保存项目信息、依赖和脚本。`npm run dev`、`npm run build` 是否存在、具体执行什么，要看其中的 `scripts` 配置。

**脚手架 Scaffold：** 创建项目初始目录和配置的工具或模板。可以类比为先搭好一个可继续施工的基础工程。它与编程语言、运行环境不是一回事。

### 3.6 Element Plus：现成界面控件

**它是什么：** 面向 Vue 3 的 UI 组件库。

**在例子里：** 用现成的表格显示商品，用表单控件录入，用弹窗确认删除。这样可以减少重复编写基础控件的工作。

它提供的是界面能力，商品从哪里来、谁能删除，仍需要项目代码处理。组件库也不能自动保证页面符合真实需求。

课件中的 **Element Plus** 和录音中的 **Element UI** 需要区分：后者常指面向 Vue 2 的那套组件库，应根据项目版本选择匹配依赖。[Element Plus 官方网站](https://element-plus.org/en-US/)

### 3.7 Pinia：不同界面怎样共享状态

**状态 State** 是程序在某一时刻记着的信息，例如当前登录用户、购物车数量、当前筛选条件。

**Pinia** 是 Vue 生态的状态管理库，可以组织组件或页面共享的状态。比如商品页加入购物车后，顶部购物车图标也要更新数量，这些界面需要读到一致的信息。[Pinia 官方说明](https://pinia.vuejs.org/introduction.html)

Pinia 中有数据，不表示这些数据已经写入数据库。刷新后是否保留，要看是否另行保存、重新请求或恢复。前端状态、浏览器本地存储、后端数据库是不同位置。

### 3.8 TypeScript：提前发现一部分用错数据的问题

**TypeScript，简称 TS** ，在 JavaScript 基础上增加类型等能力。类型可以先理解成“这个值应该是哪类数据”。

例如商品价格应是数字，若代码把它当成一个可以随意添加文字的对象，类型检查可能提前提示问题。代码中的字段名或函数参数用错，也可能被发现。

类型检查通常发生在开发或构建过程中。外部接口传来的数据仍需校验，TypeScript 不会替后端自动检查所有输入，也不会把业务逻辑自动写对。[TypeScript 新手说明](https://www.typescriptlang.org/docs/handbook/typescript-from-scratch.html)

### 3.9 axios、fetch 与 AJAX：页面怎样向外要数据

**axios** 是发送 HTTP 请求的库。商品页可以通过它向后端请求商品列表，再把返回数据交给界面显示。它也能在 Node.js 等环境中使用。[axios 官方入门](https://axios-http.com/docs/intro)

**fetch** 是现代浏览器提供的请求接口，很多场景也能完成类似工作。

**AJAX** 是网页在不整页刷新的情况下，与服务器交换数据并更新局部内容的一类做法。它不是必须另装的一台服务器，也不等同于 axios 这个具体库。

保存一件商品后列表更新，但整个页面没重新加载，就可能涉及这种前后端交互。请求怎样组织，下一章展开。

### 3.10 App、小程序、uni-app 与 React

**B/S（Browser / Server）** 常指以浏览器为入口的系统。 **C/S（Client / Server）** 指客户端与服务端协作，用户通常使用专门客户端。独立本地软件未必有远程服务端，不能仅凭有窗口就确定为 C/S。

**原生 App** 使用对应平台的界面和运行能力。 **WebView** 可以先理解为嵌入应用中的网页显示环境，一些混合应用会使用它。Chrome 与 Chromium 也需区分：Chromium 是相关的开源项目，不能把所有 Chrome 产品组成统称为完全开源。

**小程序** 运行在微信等平台提供的环境中，有自己的组件、接口与限制。它可以访问后端，但不应保存数据库管理员密码。

**uni-app** 是跨端开发框架，可以基于相应技术与平台规则，面向 App、网页和小程序等目标开发。它的范围不限于“缩小页面后自动换排版”。不同端仍有差异，需要按目标端验证。[uni-app 官方介绍](https://uniapp.dcloud.net.cn/)

**React** 是另一套构建用户界面的库。录音里短暂提到了类似这个名字，但不足以据此确定所指的是 React 本身还是 React Native 等具体方案。这里只解释这个名字，不把原生、跨端或网页容器统一视为同一种实现。

**本章自检：** Vue 组织页面，Element Plus 提供控件，Pinia 管共享状态，axios 发请求，Vite 提供开发与构建能力，Node.js 运行开发工具。它们各做一部分工作，可以配合，但并非每个小页面都必须全部使用。

### 3.11 原型、设计稿与真正的业务页面

课程还提到了界面设计工具。以 **墨刀** 这类产品为例，可以通过拖拽组件等方式组织页面原型和交互想法。[墨刀帮助中心](https://modao.cc/hc/)

**原型 Prototype** 重点帮助讨论流程和布局； **设计稿** 还会表达颜色、字体、间距等视觉细节。一个能点击的原型，不必然已经连接真实后端与数据库。

有些工具可以生成代码，但生成到哪一步、代码能否直接用于目标项目，需要具体检查。不能把“界面已经做出来”与“整个系统可以正式使用”当成同一结果。

## 04 点击按钮后，请求怎样往返

### 4.1 API 是什么，为什么页面要“调接口”

**API（应用程序编程接口）** 是程序使用另一部分能力的约定。在本课 Web 场景中，可以先理解为后端对外提供的调用入口。

例如商品后端约定：

| 操作 | 示例约定 | 意思 |
| --- | --- | --- |
| 查询列表 | `GET /api/products` | 读取商品列表 |
| 新增商品 | `POST /api/products` | 提交一件新商品 |
| 查询详情 | `GET /api/products/7` | 读取编号为 7 的商品 |
| 修改商品 | `PATCH /api/products/7` | 按约定修改部分字段 |

这里只是解释接口的示例，没有声称这些地址已经部署。接口设计不只包含地址，还应说明参数、数据格式、权限、成功结果和错误情况。

“调用”就是按约定发出要求并取得结果。前端调用后端，后端也可以调用其他公司的服务，或调用自己系统中的其他部分。

### 4.2 URL、IP、域名、端口与路径

看这个教学用地址：`http://localhost:8000/api/products?page=1&pageSize=20`。

| 部分 | 解释 |
| --- | --- |
| `http` | 使用的通信协议 |
| `localhost` | 当前这台设备自己 |
| `8000` | 端口号，用来定位这台设备上的网络服务 |
| `/api/products` | 路径，后端根据它决定调用哪项能力 |
| `?` 后面的部分 | 查询参数，这里表示页码与每页数量 |

**IP 地址** 用于网络寻址。 **域名** 是便于记忆的名字，通常由 DNS 等系统帮助解析。 **URL** 是包含协议、位置和路径等信息的完整资源地址。

`localhost`、`127.0.0.1` 一般指本机回环地址。手机输入 localhost，访问的是手机自己；把电脑上的 localhost 发给朋友，朋友也不会因此连到你的电脑。

**监听端口** 是服务开始在某个地址与端口接收连接。程序已安装、已启动、已监听、外部可达，是需要分别确认的状态。

### 4.3 HTTP、请求与响应

**HTTP** 是 Web 常用的通信协议。 **请求 Request** 是调用方发出的消息， **响应 Response** 是接收方返回的消息。[MDN HTTP 概览](https://developer.mozilla.org/en-US/docs/Web/HTTP/Overview)

请求里经常有：

- **方法 Method：** 例如 GET、POST，说明想进行哪类操作。
- **地址与路径：** 说明找哪个服务的哪项能力。
- **标头 Headers：** 补充格式、认证等信息。
- **请求体 Body：** 需要提交的数据，例如商品名称与价格。

响应通常有状态码、标头和响应体。响应体可以是 JSON、HTML、图片、文件等，并不总是 JSON。

### 4.4 JSON：逐行看懂接口数据

JSON 是一种数据表示格式。假设后端返回：

```json
{
  "code": 0,
  "message": "OK",
  "data": {
    "items": [
      {"id": 7, "name": "水杯", "price": 29.9}
    ],
    "total": 18,
    "page": 1,
    "pageSize": 20
  }
}
```

逐层读：

1. 最外层 `{}` 是一个 **对象 Object** ，里面按名称保存不同字段。
2. `"message": "OK"` 是一对字段名与值。字符串使用双引号，数字通常不加引号。
3. `data` 的值又是一个对象，里面放业务结果。
4. `items` 的值是一个 **数组 Array** ，用 `[]` 表示，可以放多件商品。
5. 每件商品又有编号、名称、价格。
6. `total`、`page`、`pageSize` 用来表达分页信息。

**序列化 Serialization** 是把程序中的数据转换为便于传输、保存的表示；转换为 JSON 文本是常见例子。接收方再把文本解析成可使用的数据。

`code`、`message` 等名字只是本例约定，不是所有接口必须这样返回。JSON 可以放在文件里，也可以直接作为网络消息传输，因此不能只把它理解为某一种文件后缀。

### 4.5 分页、轮询、同步与异步

**分页 Pagination：** 数据很多时，分批取得。例如共有 18 件商品，每页最多 20 件，第一页可以返回全部 18 件；如果共有 1,000 件，就不必第一次全部下载。

**轮询 Polling：** 隔一段时间再发一次请求。例如每隔 10 秒询问是否有新通知，页面无需人工刷新也能更新。它会产生重复请求，不是所有实时更新都必须用轮询。

**同步与异步：** 可以先从“等待期间怎样安排其他工作”来理解。程序等待网络响应时，可以按异步方式继续安排其他任务，再在结果回来后处理。具体行为取决于语言和运行方式。

异步不等于更少的数据，也不等于一定更快。下载大文件仍要时间，数据库慢查询仍然需要优化。后端中的异步与消息队列也不是完全相同的概念。

### 4.6 HTTP 状态码与业务状态码

| 常见 HTTP 状态 | 大意 | 初步检查 |
| --- | --- | --- |
| 200 / 201 | 请求成功处理 / 创建成功 | 再看返回数据是否符合业务预期 |
| 400 | 请求有问题 | 参数、格式或接口约定 |
| 401 | 缺少有效认证等 | 登录状态、认证信息 |
| 403 | 请求被拒绝 | 权限与相关规则 |
| 404 | 资源或路径未找到 | 地址、方法、路由和转发配置 |
| 500 | 服务端内部错误 | 后端日志和异常 |

**HTTP 状态码** 与上例 JSON 里的 **`code: 0`** 分属不同层次。HTTP 可以返回 200，而业务结果表示操作未完成；是否采用这种设计要看项目约定。

课堂把 `code: 0` 作为成功示例时，不应把 0 记成通用 HTTP 成功码。

### 4.7 用 F12 把这些词对应到界面

在自己有权调试的练习网站中，用 Chrome 或 Edge：

1. 按 `F12`，部分电脑用 `Fn + F12`。
2. 打开 `Network`（网络），保持面板打开后刷新页面。
3. 执行一次查询或保存，找到对应请求。
4. 看 `Headers`（标头）：地址、方法、状态等。
5. 看 `Payload`（载荷）：提交了什么；某些请求没有请求体。
6. 看 `Response`（响应）或 `Preview`（预览）：后端返回什么。
7. 出现前端异常时，再看 `Console`（控制台）；想看元素与样式时，看 `Elements`（元素）。

如果过滤后没有请求，先切到 `All`（全部）。没有请求发出，就先查前端操作；请求发出但返回错误，再沿后面的服务排查。

**本章自检：** 现在看到“前端通过 axios 调 API，后端返回 JSON”，可以翻译成：页面借助请求工具，向约定入口发消息，后端把结果按约定格式发回来。

## 05 后端怎样处理业务

### 5.1 为什么页面后面还需要一个程序

浏览器中的代码运行在用户设备上，用户能够查看、修改一部分行为。商品价格、库存和权限等关键规则，需要由可信的服务端检查。

假设某人直接发请求，把商品价格填成负数。即使网页输入框已经限制价格，后端仍需要独立检查，不能认为“正常页面不会这样发，所以一定没问题”。

另外，数据库连接、支付接口密钥等不应交给浏览器。后端可以按权限与规则访问这些能力，再返回允许展示的结果。

**服务器 Server** 在口语里有两种含义：一是承载程序的机器或计算资源，二是向外提供服务的程序。 **服务端 / 后端** 通常指程序承担的角色，不必是一台独占机器。

### 5.2 Controller、Service、Mapper：一次保存内部怎样分工

以一个常见 Java 项目的组织方式说明：

以保存商品为例，Controller 接收请求并组织响应，Service 检查价格、权限和商品状态等业务规则，Mapper 或 Repository 访问数据库，数据库保存记录。

- **Controller，控制器：** 像服务入口。它知道某条请求应该交给哪个处理逻辑。
- **Service，业务服务：** 保存“哪些操作允许、按什么顺序执行”等规则。
- **Mapper，映射器 / 数据访问部分：** 在 MyBatis 场景中组织 SQL 与结果映射。
- **Repository，仓库接口：** 另一种常见的数据访问组织方式，具体实现取决于框架。

这些名字描述职责，不是四台必须分别购买的机器。它们完全可以是同一个后端项目中的不同文件。不同语言和项目也可能使用其他目录与命名。

### 5.3 Java、JDK、JVM、JAR 与 Tomcat

**Java：** 编写程序的语言，可以用于后端。Java 不是 JavaScript，也不是 Spring Boot 的同义词。

**JDK（Java Development Kit）：** Java 开发工具包，通常包含编译、运行等所需工具。可以先理解为准备 Java 开发与构建能力的一套工具。

为解释运行，再补充 **JVM（Java Virtual Machine，Java 虚拟机）** ：很多 Java 程序先编译为字节码，再在 JVM 上执行。代码文件、构建产物和运行程序因此不是同一个东西。

**JAR：** Java 中常见的打包格式。有些应用被构建为可启动的 JAR，但能否直接启动要看打包方式与运行条件。 **WAR** 是传统 Java Web 部署中常见的另一种打包格式。

**Tomcat：** 常见的 Java Web / Servlet 容器。Servlet 可以先理解为 Java Web 中处理请求的一套标准接口。Tomcat 帮助相应 Java Web 应用接收和处理 Web 请求。

**Nginx 与 Tomcat 可以配合，但不是同一个东西。** Nginx 可以先接入并转发，后面的 Tomcat 承载 Java Web 应用。Spring Boot 的常见 Web 项目可以内嵌 Tomcat 等服务器，不必一律先独立安装 Tomcat。[Spring Boot 内嵌服务器说明](https://docs.spring.io/spring-boot/how-to/webserver.html)

### 5.4 Spring、Spring MVC、MyBatis、Spring Boot

把这几个名字当成不同职责理解：

**Spring / Spring Framework：** Java 生态的重要应用框架。它提供组织和协作应用组件等能力。初学可先理解为：帮助应用把各部分对象与功能接起来，具体机制以后再学。

**Spring MVC：** Spring 中构建 Web 应用的一套能力，涉及请求怎样对应到处理方法、参数怎样取得、结果怎样返回等。前面的 Controller 经常与它有关。

**MyBatis：** 数据持久化框架，帮助执行自定义 SQL、设置参数、把结果映射为 Java 可用的数据。它在后端与数据库之间工作，但数据库仍是另一部分软件。[MyBatis 官方介绍](https://mybatis.org/mybatis-3/)

**Spring Boot：** 帮助创建、配置和运行 Spring 应用，减少常见配置工作，提供便于组合依赖和运行服务的方式。它不是另一门编程语言。[Spring Boot 官方介绍](https://spring.io/projects/spring-boot/)

四者可能这样配合：Spring Boot 帮项目搭建和启动，Spring MVC 接收 Web 请求，业务代码处理商品规则，MyBatis 把商品数据写入数据库。

### 5.5 SSH、SSM：为什么课程介绍历史组合

这里的 **SSH** 是 **Struts2 + Spring + Hibernate** 的组合缩写。 **Struts2** 是 Java Web 框架， **Hibernate** 是 ORM 框架，帮助组织对象与关系型数据的映射。ORM 在下一章解释。

这里的 **SSM** 是 **Spring + Spring MVC + MyBatis** 的组合缩写。

讲这些历史组合，是为了理解“接请求、处理业务、访问数据”等分工如何组织。它们不是两个单独的编程语言，也不能因为某个组合较早，就推断组成它的每个项目都已经停止维护。

还有另一种 **SSH（Secure Shell）** 是安全远程连接协议。部署时“通过 SSH 登录服务器”和这里的 Java SSH 组合，含义完全不同。

### 5.6 Spring Cloud、微服务、实例、并发

**单体应用：** 多项业务在一个整体应用中组织和部署。内部仍然可以清楚分模块，代码不一定混乱。

**微服务：** 把系统拆为若干可以相对独立开发、部署的服务，它们通过网络等方式协作。例如商品服务和订单服务分别运行。拆开后，也增加了网络通信、配置、故障处理与数据协作的工作。

**实例 Instance：** 同一个服务实际运行的一份。为了处理更多请求，可以把同一个商品应用运行三份。这是多个实例，不必等同于三个不同微服务。

**并发 Concurrency：** 在一段时间里同时处于处理过程中的任务或请求。总注册用户 10 万，并不代表每一秒有 10 万人在同时操作。

**Spring Cloud：** 为分布式系统中的配置、服务发现、路由、服务调用等问题提供相关工具。它可以建立在 Spring Boot 应用之上，二者可以配合。[Spring Cloud 官方介绍](https://spring.io/projects/spring-cloud/)

不能仅按用户数、页面数或功能模块数，断言某个框架必须换掉。还要看请求复杂度、数据量、响应要求、团队维护能力与实际测量结果。课堂的大小项目例子适合帮助建立选型意识，不是固定性能边界。

### 5.7 Nacos、Gateway、OpenFeign、Sentinel

以商品服务、订单服务分开运行的情况解释：

**Nacos：** 可以提供服务注册发现、配置管理等能力。“服务发现”帮助找到服务的可用实例；“配置管理”帮助管理需要分发和更新的设置。它不负责自动写出商品业务。

**Spring Cloud Gateway：** API 网关，按规则把请求路由到相应服务，并可以执行认证相关处理、监测等过滤逻辑。网关是系统入口职责，具体是否采用它与其他接入服务，要看架构。

**OpenFeign：** 帮助用声明式方式组织 HTTP 客户端调用。例如订单服务需要查询商品服务，可以用相应方式定义调用。它不是数据库，也不表示所有服务之间的调用都必须绕网关。

**Sentinel：** 流量控制、熔断等保护组件。 **限流** 是限制进入的请求量； **熔断** 可先理解为某个依赖持续出错时，暂时停止或改变调用，避免故障继续扩大。[Sentinel 官方说明](https://sentinelguard.io/en-us/docs/introduction.html)

这些组件不需要在第一个小接口中全部出现。课件列出它们是在介绍可用能力，而不是提供每个项目通用的必装套餐。

### 5.8 Python、Django、Flask、FastAPI

**Python：** 编程语言。运行普通 Python 程序通常需要相应解释器和依赖。后端框架是在这门语言上提供 Web 能力。

**Django：** 包含较多常用 Web 能力的框架，例如 ORM、管理后台、用户认证等。适合想复用这些约定和功能的项目，但仍需编写业务代码、配置和验证。[Django 官方概览](https://docs.djangoproject.com/en/stable/intro/overview/)

**Flask：** 较轻量的 Web 框架，提供基础机制，并可以通过扩展等方式组合更多功能。“轻量”说明核心设计与组合方式，不能直接等同于只能承受少量用户。[Flask 官方说明](https://flask.palletsprojects.com/en/stable/)

**FastAPI：** 构建 API 的框架，利用 Python 类型提示等能力进行数据校验、生成接口描述与文档，也支持相应异步使用方式。它能减少一些重复工作，仍不会替你自动完成全部业务与权限。[FastAPI 功能说明](https://fastapi.tiangolo.com/features/)

FastAPI 常用的 `/docs` 页面是供开发者查看、试调接口的界面。它不是顾客最后使用的商品网站。Python Web 应用还需要合适的运行服务器和部署配置，不能概括成“Python 永远不用额外的 Web 运行组件”。

### 5.9 Go、Gin、goroutine

**Go，也叫 Golang：** 编程语言，常能构建为便于分发的可执行程序。需要按目标操作系统、CPU 架构构建，并检查外部依赖、资源和配置。Windows 的 exe 不会因此自动变成 Linux 原生程序。

**Gin：** Go 的 Web 框架，提供路由、参数处理等能力，帮助组织后端接口。[Gin 官方文档](https://gin-gonic.com/en/docs/)

**goroutine：** Go 语言中组织并发执行的机制，可理解为由 Go 运行时管理的轻量执行任务。它能帮助安排工作，但不会自动解决所有共享数据、顺序与错误处理问题。

### 5.10 若依、芋道、“全家桶”与二次开发

录音提到了若依、类似“芋道”的名字以及现成开源工程。 **全家桶** 是口语，通常表示已组合若干框架、基础页面和通用功能；不同项目包含什么，必须看实际版本与说明。

**二次开发，简称二开：** 在已有代码或产品基础上修改、扩展。比如已有登录、菜单、用户管理，再添加商品模块。

**开源** 使代码可以按相应许可获得和使用，不意味着无需看许可、无需理解代码，或没有维护成本。拿来工程后，要先确认来源、版本、依赖和运行步骤，再确定自己的修改位置。这里没有凭录音选定若依或芋道的某个具体仓库。

**PHP 与 .NET：** 课程也简短提到。PHP 是语言，.NET 是包含运行时、开发工具和框架的平台生态；它们仍有受支持的版本，不能把课堂口语直接记成“已经全部淘汰”。[PHP 支持说明](https://www.php.net/supported-versions.php)、[.NET 支持政策](https://dotnet.microsoft.com/en-us/platform/support/policy)

**中间件 Middleware** 是课程中的一个概括性称呼，在不同语境可指基础服务软件，也可指框架内处理请求的一段机制。听到它时应追问实际产品与职责，不把所有东西当成同一种软件。

**本章自检：** 学一条后端路线，是选语言与对应工具把一个请求处理完。认识其他路线用于判断和接手项目，不要求 Java、Python、Go 同时学习。

## 06 数据库怎样保存和查询数据

### 6.1 数据库、表、字段、记录、ID

先把商品表想成一张有明确规则的表格：

| id | name | price | stock | status |
| --- | --- | --- | --- | --- |
| 7 | 水杯 | 29.9 | 50 | 已上架 |
| 8 | 笔记本 | 12 | 100 | 未上架 |

- **数据库 Database：** 管理数据的一套系统；口语里也可能指其中一个具体数据库集合。
- **表 Table：** 保存某类记录的结构，例如商品表。
- **字段 / 列 Column：** 例如名称、价格，每个字段通常有对应类型与规则。
- **记录 / 行 Row：** 一件商品的这组信息。
- **ID：** 标识数据的编号或标识值。
- **主键 Primary Key：** 在表中唯一标识记录的字段或字段组合，不一定必须叫 id。

数据库不仅保存表格，还负责查询、约束、并发访问等工作。结构化数据强调有明确的结构与字段约定，不能把“放在文件里”直接等同于“没有结构”。

### 6.2 SQL 与增删改查

**SQL** 是用于定义、查询和操作关系型数据的语言。 **MySQL** 是一种数据库软件。可以理解成“使用 SQL 向 MySQL 表达要求”。

**CRUD** 是新增 Create、读取 Read、更新 Update、删除 Delete 的缩写，中文常说“增删改查”。

先看一条查询示意：

```sql
SELECT id, name, price
FROM products
WHERE id = 7;
```

逐行意思：从 `products` 商品表中，找出编号为 7 的记录，返回编号、名称、价格三个字段。

**WHERE** 是条件。 **LIKE** 可按模式匹配文本，例如某些包含指定字词的名称查询。具体效率与匹配写法、索引和执行方式有关。

上例用于解释语言，实际运行前需要对应数据库、表和数据。真实程序应使用参数化查询，不能直接把用户输入拼成 SQL。

### 6.3 MySQL、PostgreSQL、SQLite、Oracle

它们都是课程提到的关系型数据库，但运行、特性、管理方式并不完全相同。

**MySQL：** 常以独立数据库服务运行。后端使用地址、端口、账号和数据库名称等信息连接它，适合学习“应用连接一个数据库服务”的过程。

**PostgreSQL：** 另一种关系型数据库，提供较多数据类型和扩展能力。本课的 pgvector 就运行在其扩展生态中。它不是 MySQL 的另一个名字。

**SQLite：** 数据库引擎可嵌入应用，直接读写数据库文件，不需要再启动一个独立数据库服务器进程。适合许多本地或嵌入式场景，也可用于入门练习，但仍需备份与正确处理并发等问题。[SQLite 官方说明](https://www.sqlite.org/serverless.html)

**Oracle Database：** 商业数据库产品，在一些组织的系统中使用。认识其类别即可，是否使用取决于具体项目要求，不能只根据“新或旧”决定。

录音也提到了 **达梦** 和 **东方通** 相关名字。达梦有数据库产品，东方通有中间件等产品，不能把公司名、产品类别与技术来源混在一起，更不能据一句口语断言它们都来自 MySQL。本笔记不复述这类未证实的来源概括。[达梦技术文档](https://eco.dameng.com/)、[东方通产品资料](https://www.tongtech.com/)

共同概念可以迁移，但从一种数据库切换到另一种，还要检查 SQL 方言、字段类型、事务行为、驱动与工具等，可能不只是改几个单词。

### 6.4 索引：查数据为何不一定逐行翻找

**索引 Index** 可以类比一本书的目录或索引页：为了更快定位符合某些条件的数据，数据库维护额外的数据结构。

例如经常按商品编号查询，可以利用适当索引定位；这与每次从第一件商品逐条查到最后，过程不同。

索引也占空间，写入时需要维护，而且不是给每列加一个就都快。慢查询要看具体 SQL 和执行情况。不能先假定“数据库一定慢，必须把全部数据搬到 Redis”。[MySQL 索引说明](https://dev.mysql.com/doc/refman/8.4/en/mysql-indexes.html)

### 6.5 事务：一组操作怎样共同完成

**事务 Transaction** 把一组相关数据库操作作为一个整体处理。先用库存例子理解：创建订单和扣减库存，如果只成功一半，数据就可能不一致。

在合适的数据库与正确的事务设计下，可以让相关操作共同提交，或在失败时回滚。 **回滚 Rollback** 在这里指撤销未完成事务的修改，与 Git 代码回退不是同一件事。

数据库事务不能自动覆盖所有外部系统。若同时调用付款平台，外部调用和本地数据库怎样保持一致，还需进一步设计。

### 6.6 ORM、驱动与 MyBatis

程序要连接数据库，需要相应的 **数据库驱动** 等通信能力。为了减少重复组织字段和结果的代码，还会使用数据访问工具。

**ORM（对象关系映射）** 可以先理解成：把程序中的对象、属性，与数据库中的表、字段联系起来。对象是程序里组织一件数据的方式，例如一个商品对象含有名称和价格。

Hibernate、Django ORM 是相关例子。MyBatis 更强调自定义 SQL 与结果映射，不应把它理解为自动管理数据库所有行为的总控制器。

完整分工可以这样记： **业务代码决定要做什么，数据访问工具组织调用，数据库真正执行相应数据操作。**

### 6.7 多张表与复杂业务

课堂用学生信息举例：姓名在学生表，家庭成员在关系表，成绩在成绩表，作业情况在其他表。一次页面查询可能需要组合这些信息。

补到商品网站：商品基础信息、库存记录、订单明细和供应商联系方式，也可能在不同表中。后端可以通过合适 SQL、多个查询等方式组织结果，再返回页面。

**关联 / JOIN** 是按相关字段组合关系型数据的常见方式，具体做法需要结合结构与需求。不是必须“每张表都各查一遍，再全部交给前端拼”。

**第三方 API** 是其他系统提供的接口。若商品配送信息来自物流系统，后端还要调用那个服务，处理超时、失败和返回格式。这是课程后半段“复杂调用”的重要补充：后端可能同时协调数据库和外部服务。

**消息队列 Message Queue** 可以帮助把一些工作通过消息交给其他处理者，例如下单后安排发送通知。它涉及异步处理、失败重试和重复消息等问题，并不自动保证所有数据一致。课程只是带到这个名字，没有完整教学。

**本章自检：** 商品表负责保存记录，SQL 表达查询要求，索引帮助查找，事务组织相关操作，ORM / MyBatis 帮程序更方便地访问数据。它们处在不同层次。

## 07 缓存、文件与搜索为什么要分开

### 7.1 先把“数据”拆成几种需求

同一件水杯，在系统里可以同时有商品记录、照片、用户搜索时需要的文本信息。它们相互关联，但用途不同。

| 信息或需求 | 例子 | 常见处理方式 |
| --- | --- | --- |
| 业务事实 | 价格 29.9、库存 50 | 关系型数据库保存记录 |
| 文件本体 | 水杯照片、说明书 PDF | 文件系统或对象存储 |
| 重复读取的结果 | 热门商品详情的缓存副本 | 按需使用 Redis 等 |
| 按文本搜索 | 搜“保温杯”找到相关商品 | 全文索引等 |
| 按意思找相近内容 | 用另一种说法找商品说明 | 向量或混合检索等 |

“都叫数据”不表示必须全部使用同一种存放方式。但简单项目也不需要预先引入表中所有工具。

### 7.2 Redis：为什么要缓存，缓存又有什么麻烦

**Redis** 是主要以内存提供快速数据访问的服务，能使用多种数据结构。课程主要用它解释缓存。

**内存 RAM** 用于运行中的快速访问， **磁盘** 等存储用于长期保存。数据库自身也有缓存机制，所以不能简单把数据库理解成每一步都直接读磁盘。

**缓存 Cache** 是保存一份便于重复读取的数据。比如很多人都在看同一件商品，可以按设计先读缓存，未命中再查主库，把适合缓存的结果保存一段时间。

查询商品详情时，先判断缓存是否有可用结果。有结果则按缓存规则返回；没有则查询主数据库，再按规则写入缓存。

**TTL / 过期时间** 是缓存或键还能保留多久。缓存还会有失效、淘汰和更新的问题。

例如主库把价格由 29.9 改成 19.9，缓存仍是 29.9，就可能显示旧价。因此引入 Redis 的同时，要设计修改后怎样失效或更新缓存。课堂“学校信息变化少”的例子是在帮助理解适合缓存的情况，不是所有缓存都必须在服务启动时装载全库。

Redis 也有持久化等能力，不能记成“一关机所有数据必然消失”；能保留哪些数据、容忍多大丢失，需要看配置与设计。[Redis 持久化说明](https://redis.io/docs/latest/management/persistence/)

### 7.3 MinIO、对象存储、桶、对象键与 S3

**对象存储 Object Storage** 把文件内容和相关信息作为对象存放，并通过相应接口访问。图片、视频、文档等常见于这类场景。

**MinIO** 是课件用来介绍对象存储的产品。可以先理解为给应用提供文件存取接口的一项服务。 **AWS S3** 是相应云对象存储服务； **S3 兼容接口** 指实现了相应范围的接口约定，不保证所有产品功能完全相同。

**桶 Bucket** 是组织对象的容器，可以类比一组存储空间。 **对象键 Object Key** 是对象在其中的标识，例如 `products/7/photo.jpg`。

商品表中可以记录这个对象键、文件类型、所属商品等；文件本体放在对象存储。需要展示时，再取得允许访问的地址。

**阿里云 OSS、腾讯云 COS** 是课程提到的云对象存储服务。它们与自建服务的部署、认证、权限和接口细节可能不同，迁移时应核对这些条件，不应默认“只改一个地址，其他全部一样”。

**私有对象** 不应因为知道文件路径就随意访问。可以按需要通过后端授权或有时效的访问方式提供文件，具体取决于存储方案。

### 7.4 FTP、BLOB，以及“文件不进数据库”的含义

**FTP（文件传输协议）** 是传输文件的一种协议，也常有相应客户端与服务器。它与对象存储不是同一套机制，不能把“MinIO”直接翻译成“FTP”。

**BLOB** 是保存二进制大对象的一类数据库字段。图片、文件可以技术上保存在这类字段中。

课程强调把文件本体单独存放，是在讲一种常见工程选择：文件分发、备份、权限和业务记录可以分别组织。是否放数据库仍取决于规模和需求，不是技术上绝对禁止，也没有适用于全部项目的固定性能倍数。

**文件系统、对象存储、网盘** 也需要区分。网盘是面向使用者的产品，能否可靠地供程序读写，还要看接口、权限与服务约定，不能因为能手动上传就认定适合作为应用存储后端。

### 7.5 Elasticsearch、全文搜索、分词与 IK

**Elasticsearch，常缩写为 ES** ，是用于搜索与分析的服务。它擅长围绕索引组织文档搜索、相关性排序、过滤与聚合等。

**全文搜索** 关注文字内容。例如在很多商品说明或合同里搜“自动续约”，希望按内容找到相关文档，而不仅是按编号查某一条记录。

**分词 / 文本分析** 把原文处理成适合建立搜索索引的词项等表示。 **IK** 是课件提到的中文分析社区插件，需要关注安装、词典、配置与版本匹配，不能默认任何 Elasticsearch 安装后就已带有 IK。[Elastic 分析插件说明](https://www.elastic.co/docs/reference/elasticsearch/plugins/analysis-plugins)

**聚合 Aggregation** 可以先理解为在符合条件的数据上分组、计数、计算统计值，例如按商品类别统计数量。

ES 不只是把全部内容放进内存，它涉及索引、磁盘、内存等。它与关系型数据库的事务及数据建模能力也有差异。课程的业务示例里，把主库作为业务记录依据，把 ES 作为可重建的搜索索引，是一种容易理解的设计；不必扩张成所有系统的主库永远只能是 MySQL。

### 7.6 课堂合同案例：把文件、文字、记录和搜索接起来

课程讲过一个比商品列表更复杂的场景：上传合同 PDF 或照片，再根据合同正文搜索。

上传合同后先保存原始文件，再提取文字；扫描件可能需要 OCR。业务数据库保存合同编号、甲乙方和文件关联，需要全文搜索的内容另建索引。搜索命中后仍要关联回有权限访问的合同和文件。

**OCR（光学字符识别）** 是从图片等内容中识别文字的技术。已经包含文本的 PDF 可以尝试直接提取文字，扫描图像则通常需要 OCR，识别结果还可能有误。

这解释了为什么“文件已经上传成功”与“能搜索正文”是两件事：中间还要取得文字、建立索引。新增、修改或删除合同后，也要同步处理相应搜索内容。

### 7.7 FFmpeg 在这张地图里的位置

**FFmpeg** 是音视频处理工具，可用于转码、裁剪、合并、提取音轨、抽取视频帧等。通常由后端程序或脚本调用，也可以通过命令行使用。

例如店员上传一段商品视频，系统需要压缩成合适格式、生成封面，可能会用到它。

它不负责商品权限或订单存储，也不能因为出现在 AI 视频处理流程中，就被当成生成式视频模型。没有音视频需求的商品练习，可以先不涉及。

**本章自检：** 主库、缓存、文件、搜索索引可以服务同一个功能，但它们保留的是不同用途的信息，更新、权限和备份需要一起考虑。

## 08 Linux 与 Docker 怎样承载服务

### 8.1 Linux 与那些发行版名字

**操作系统 OS** 管理程序运行、文件、网络和硬件资源。Windows、Linux 等属于这一层。

**Linux** 严格说是内核名称，日常也常用来泛指相关操作系统。 **内核 Kernel** 是操作系统中管理底层资源的核心部分。

课程提到的 **Ubuntu、Red Hat / 红帽、CentOS、SUSE** ，属于相关 Linux 发行版或产品家族。可以先理解为围绕 Linux 组合工具、软件包和管理方式形成的不同系统方案，不是四种后端语言。

服务器经常不装桌面环境，通过远程命令行管理；Linux 也可以有桌面。不同发行版和版本的支持状态、包管理方式可能不同，安装时按实际项目要求选择。

### 8.2 文件系统与跨平台运行

**文件系统** 组织磁盘上的文件和目录。课程提到 FAT32、NTFS、ext3、ext4，是相关格式名称。

但程序能否跨系统运行，还取决于可执行格式、系统接口、CPU 架构和依赖，不能只用“磁盘格式不同”解释。普通图片和文本也不等于只能在一种系统上查看。

Linux 同样可能存在漏洞、恶意程序和错误配置。系统安全还取决于更新、权限、暴露的服务与实际管理，不能依靠“用了 Linux 就不会出问题”的印象。

### 8.3 PATH：为什么装了 Java，终端却找不到

**环境变量 Environment Variable** 是进程获得配置的一种方式。 **PATH** 是其中一个常见变量，告诉命令行到哪些目录寻找可执行程序。

例如 `java` 已安装在某个目录，但这个目录不在当前终端的 PATH 中，直接输入 `java` 仍可能提示找不到命令。课程现场遇到过类似现象。

**绝对路径** 完整指出文件位置， **相对路径** 则要结合当前目录理解。AI 使用绝对路径找到了程序，而人直接输入命令找不到，并不矛盾。

新开终端、检查安装目录与 PATH，常是相关排查步骤。不要因为一次命令不识别就反复安装不同版本。

课程顺带提到 **C 与 GCC** ：C 是语言，GCC 是编译工具集合，可用来编译相应代码。同样属于“语言与工具要分开”的例子，并不是所有 Web 项目都需要再装它。

### 8.4 Docker：环境不一致的问题怎样减少

假设本地用了某个 Python 版本、一组依赖，另有 MySQL 和文件存储服务。放到另一台机器时，版本、配置、路径等可能不同，导致启动失败。

**Docker** 提供构建、分发和运行容器等能力。可以把应用需要的文件和依赖按明确方式组织起来，让启动过程更容易复现。[Docker 容器说明](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/)

**容器 Container** 是在隔离环境中运行的进程等资源组织形式。Linux 容器通常共享承载环境的 Linux 内核，不是每个容器自带一套完整独立内核。

因此 Docker 能减少环境差异，但不会消除 CPU 架构、系统条件、外部服务、文件权限、网络和配置方面的全部问题。

### 8.5 镜像、容器、Docker Desktop、Dockerfile

| 名称 | 怎样理解 | 在例子里 |
| --- | --- | --- |
| 镜像 Image | 创建容器所用的文件与启动配置等模板 | 一份包含商品后端及依赖的镜像 |
| 容器 Container | 从镜像创建并运行的实例 | 正在运行的商品后端 |
| Docker Desktop | 本地开发中管理和使用容器的一套产品 | 在 Windows 上查看、启动、停止容器 |
| Dockerfile | 描述镜像怎样构建的文件 | 指明基础环境、复制哪些文件、怎样启动 |

Dockerfile 是为理解流程补充的术语，课程没有逐行教学。Docker Desktop 的图形界面也不是服务器必须拥有的业务界面。

**虚拟机 VM** 通常提供包含独立操作系统内核的虚拟环境，与容器的隔离方式不同。Windows 上运行 Linux 容器时，通常需要相应虚拟化承载环境，不能简单把两者混成一种。

### 8.6 端口映射、网络与 localhost 的陷阱

容器里的后端可能监听自己的 8000 端口。为了让电脑访问，可以配置宿主机某个端口转到它，这叫 **端口映射 Port Mapping** 。

**宿主机 Host** 是承载这些容器的环境。宿主机上的端口号与容器内部端口号可以不同。

当应用在容器里运行时，`localhost` 通常指该容器自己的网络环境。若数据库在另一个容器，不能随意把数据库地址写成 localhost，而需要正确的服务名或地址与网络配置。

这也是“本地能连数据库，放进容器就连不上”的常见原因之一。其他原因仍可能是权限、服务状态、端口和配置。

### 8.7 数据卷：删掉容器后，数据怎样保留

**持久化 Persistence** 是让数据在进程、容器等生命周期之外仍有正确的保存方式。

**数据卷 Volume** 可以把需要保留的数据与容器可写层分开。数据库和上传文件通常要特别设计持久化位置。[Docker 数据卷说明](https://docs.docker.com/engine/storage/volumes/)

镜像能重新下载，不能据此认为业务数据也能重新下载。数据卷也不等于备份：误删除、错误写入或磁盘故障仍可能影响其中的数据。

### 8.8 Docker Compose：多个服务怎样一起组织

**Docker Compose** 用配置文件描述一组服务、网络、数据卷等，并帮助统一创建和启动。[Docker Compose 官方说明](https://docs.docker.com/compose/)

在商品项目里，可以分别有后端容器、数据库容器、需要时才加入的文件存储容器。服务互相连接，但不需要全部塞进同一个容器。

课堂图把很多工具放在一个大框里，适合表达“一组运行依赖”；具体实施时，要再区分镜像、容器、配置与业务数据，不能直接把那幅图当成完整部署配置。

### 8.9 ENV、.env 与不同环境的配置

**ENV** 是环境变量的常见简称。 **`.env`** 是常见的配置文件命名约定，需要由应用、工具或相关库按规则加载。

例如开发环境连接测试库，生产环境连接正式库。代码可以读取相同配置名，但实际配置值不同。

文件存在不等于配置自动生效。把配置写到前端构建中，某些值可能进入用户可下载的文件，因此服务器密钥不能因此变安全。具体密钥管理与 `.gitignore` 在后面继续说明。

**本章自检：** 知道当前运行的是哪个服务，在哪个环境、监听什么端口、连接哪里，以及数据放哪，比仅仅看到 Docker Desktop 中一排绿色状态更有用。

## 09 Git 怎样帮助管理修改

### 9.1 为什么仅保存文件还不够

假设商品列表本来正常，AI 修改后打开变成空白。如果只保存了最新文件，又没有记录，就很难分清改了哪里、怎样回到可用状态。

**Git** 是版本控制工具，可以记录一组文件在不同时间的状态，查看差异、组织协作与版本历史。[Git 官方入门](https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F)

**仓库 Repository，简称 Repo** 是 Git 管理项目内容和历史的单位。 **本地仓库** 在当前电脑， **远程仓库** 是可通过网络协作的一份仓库。

### 9.2 工作区、暂存、提交、推送

| 动作或位置 | 发生什么 |
| --- | --- |
| 工作区 Working Tree | 正在查看和编辑的文件 |
| 差异 Diff | 当前版本与另一个状态相比改了什么 |
| 暂存 Stage | 选定这次准备记录哪些修改 |
| 提交 Commit | 在本地记录一个版本，并附说明 |
| 推送 Push | 把相应本地提交发送到远程仓库 |
| 克隆 Clone | 从已有仓库取得本地副本 |
| 拉取 Pull | 获取并整合远程更新，可能需要处理冲突 |

**保存文件、提交版本、推送远程、部署线上，是四个不同动作。** 除非配置了后续自动流程，否则推送完成并不表示网站已经更新。

**分支 Branch** 帮助组织不同的修改路线。 **合并 Merge** 把相应修改整合起来。 **冲突 Conflict** 表示一些修改不能由工具直接决定怎样结合，需要检查并处理。

初学时可以先学会查看状态、差异、历史与记录小步修改。不要在不了解影响时，用会丢弃本地修改的命令“强行修好”。

### 9.3 GitHub、SVN 与云效

**GitHub** 是代码托管与协作平台。它可以托管 Git 仓库，还提供 Issues（问题）、Discussions（讨论）、Actions（工作流）等功能。

**SVN / Subversion** 是另一种版本控制系统，与 Git 的工作方式不同。 **阿里云云效** 是提供代码协作、流水线等能力的平台。它们并不全属于“Git 的另一个名称”。

Git 本地功能不依赖某一个特定网站。远程网站网络不通，不等于本地 Git 无法查看差异或提交记录。

### 9.4 代码回退，不等于恢复所有线上状态

课堂讲了线上升级异常时回到旧版本。完整考虑时，还要问：旧代码能否读取现在的数据？数据库结构是否改变？配置是否改变？是否需要重新构建并部署？

Git 主要记录纳入管理的文件历史，不会自动备份数据库和所有上传文件。 **备份、恢复、代码回退、数据库事务回滚** 解决的是有关联但不同的问题。

一次小改动做完就验证、记录清楚，通常比积累大量修改后再追查更容易定位。

## 10 网站怎样让别人访问

### 10.1 构建、产物、启动、部署与联调

**构建 Build** 按项目约定把源代码转换和整理为目标环境需要的内容。 **产物 Artifact** 是构建得到的文件，例如一组前端静态资源、Java JAR、Go 可执行文件或容器镜像。

**静态文件** 是可以按文件形式发送的 HTML、CSS、JavaScript、图片等。它们被称为静态资源，不意味着页面不能交互；JavaScript 下载到浏览器后仍能执行和请求数据。

**启动 Run** 是让程序运行。 **部署 Deploy** 则还包含把合适的产物与配置放到目标环境、准备依赖、启动并验证。

**联调** 是把分别做好的部分接起来验证。例如前端不再用写死的商品列表，而是请求真实后端；后端再连接正确数据库。

### 10.2 域名、DNS、HTTPS、证书与 acme.sh

**域名 Domain** 是便于记住的名字。 **DNS（域名系统）** 帮助把名字解析到相应网络位置。购买域名、设置解析和运行应用，是不同工作。

**HTTPS** 是通过 TLS 等机制保护的 HTTP 通信，帮助保护传输并验证所连接服务的身份。它不会自动修复后端权限漏洞，也不等于数据库内容已经加密。

**证书 Certificate** 参与身份验证等过程，需要与服务配置正确配合，并关注有效期。

**acme.sh** 是课件提到的证书自动化客户端，可用于按所选证书服务与验证方式申请、续期证书。它不是域名商，也不是网站后端；续期后的证书还需正确部署和加载。[acme.sh 官方项目](https://github.com/acmesh-official/acme.sh)

**ICP备案** 是课件涉及的另一项部署事项，不能仅凭“域名在国内购买”判断。面向中国内地服务器托管等场景，需按实际服务和接入商要求核对备案条件。[阿里云网站部署与备案说明](https://www.alibabacloud.com/help/en/dws/getting-started/the-whole-process-of-website-building/)

### 10.3 Nginx、Apache、反向代理与负载均衡

**Nginx** 是 Web 服务软件，可分发静态资源、转发请求等。 **Apache HTTP Server** 是另一种 Web 服务软件；这里的 Apache 指具体产品，不是 Apache 基金会旗下所有软件。

**反向代理 Reverse Proxy** 可以先理解为服务端入口代收请求，再按规则转交内部服务。

在商品网站中，同一个域名可以这样组织：

浏览器请求先到 Nginx。请求页面文件时，它可以直接返回前端资源；请求 `/api/` 接口时，它把请求转给后端，再把后端响应返回浏览器。

**负载均衡 Load Balancing** 是把请求分配到多个服务实例。例如有三份商品后端，入口按规则分担请求。它与反向代理有关，但不是完全相同的概念。[Nginx 官方入门](https://nginx.org/en/docs/beginners_guide.html)

小练习可以直接访问后端，不一定先装 Nginx。云平台也可能承担入口、证书、静态托管等能力。

### 10.4 systemd、PM2 与进程守护

如果通过终端启动程序，关闭终端后服务停止，就需要理解启动方式与生命周期管理。

**进程守护 / 服务管理** 帮助按配置启动服务、在异常退出后重启、记录输出等。

**systemd** 是许多 Linux 系统使用的系统与服务管理器。 **PM2** 是常用于 Node.js 应用的进程管理工具。容器也可以配置适当重启策略或由其他管理系统负责。

它们不是严格按“Java 只能 systemd，Node 只能 PM2”划分。要结合运行环境选一种合适方式，并检查重启后是否仍能工作。

**日志 Log** 是程序运行时留下的信息，例如启动了什么、处理了什么、哪里出错。课件里的 `tail -f` 是持续查看文件新增内容的一种命令用法，实际应先找到对应日志文件。

### 10.5 CI/CD、GitHub Actions 与自动流程

**CI（持续集成）** 通常围绕提交后的自动构建、检查、测试等工作。 **CD** 可指持续交付或持续部署，强调后续发布过程的自动化，具体含义应结合团队流程。

**GitHub Actions** 可以按项目配置执行工作流，例如代码更新后运行检查、构建镜像，再按条件发布。[GitHub Actions 官方介绍](https://docs.github.com/en/actions/about-github-actions/understanding-github-actions)

它不是上传代码后默认自动帮所有项目上线。需要配置触发条件、运行步骤、目标环境与相应权限。

**流水线 Pipeline** 是把这些步骤按依赖组织起来的流程。先手动理解并走通流程，再自动化，更容易判断失败在哪一步。

### 10.6 验收与维护

课程强调换外部网络访问，比如手机流量，是为了验证不只本机可用。但上线验收还应验证核心功能、权限、数据保存、备份与异常处理。

最小验收可以是：另一台设备打开网页；店员新增商品成功；重启后记录仍在；普通顾客无法修改商品；失败时能找到日志。

**防火墙 / 安全组** 是控制网络连接的规则机制。网站端口是否允许访问，与应用是否启动是不同问题。不要为了排错就把所有服务端口无差别公开。

**本章自检：** 域名帮助找到入口，接入服务转发或发送文件，后端处理业务，服务管理让它持续运行，CI/CD 自动执行约定步骤。这些工作可以分开验证。

<a id="chapter-11"></a>

## 11 AI 怎样接入这套系统

先有前面的网站流程，再增加 AI 功能，更容易判断 AI 到底负责哪一段。比如想增加“根据商品说明回答问题”，并不表示原有商品表、权限和后端就全部消失。

### 11.1 大模型、LLM API、提示词、上下文与 Token

**LLM（Large Language Model，大语言模型）** 根据输入和已有训练等条件生成内容。 **模型 API** 是程序访问某项模型服务的接口。

普通后端可以接收顾客问题，再调用模型服务，最后把回答返回前端。这样，模型调用也是后端执行的一项工作。

**提示词 Prompt** 是交给模型的输入说明。 **上下文 Context** 是当前调用中可供模型使用的信息，例如问题、对话、工具返回结果和检索到的资料。

**Token** 是模型处理文本等内容时使用的计量单位之一，不宜简单理解为一个汉字或一个单词。具体切分与服务有关，也可能影响输入长度、输出限制和费用。这些是为理解模型调用补充的概念。

**API Key** 是服务用来识别、授权调用者的一类凭据。 **Token** 在认证场景中也可能指访问令牌，与上面的模型文本计量单位同名不同义。

不同模型服务的兼容接口可以减少接入差异，但换服务还要核对模型名、参数、工具能力、返回数据、额度与限制，不能默认只换地址就一定完全兼容。

### 11.2 Embedding：把内容变成便于比较的表示

**Embedding（嵌入 / 向量表示）** 是把文本等内容表示为一组数字。生成这种表示的模型，通常称为嵌入模型。

例如顾客问“这个杯子装热水会不会烫手”，商品说明里写的是“杯壁采用隔热设计”。字面不同，但合适的语义表示可能帮助找到相关内容。

**向量 Vector** 在这里是一组有确定维度的数。用相应相似度或距离方法比较向量，可以寻找相近内容。向量不是“把所有文字混成一团”，也不自动证明两段内容事实相同。

不同模型产生的向量不应默认混合比较。资料、问题使用什么模型和处理方式，需要保持适当的一致性。

### 11.3 向量检索与各个工具

**向量检索 Vector Search** 是按向量相似性寻找候选内容。存储系统通常还需要保留内容标识、来源、权限标签等信息，便于找到原始资料。

课程的几种工具可以这样理解：

| 名称 | 是什么 | 在资料问答中的位置 |
| --- | --- | --- |
| pgvector | PostgreSQL 的向量扩展 | 希望在 PostgreSQL 中组织相关向量检索时，可评估它 |
| Chroma / ChromaDB | 提供资料、向量和检索等能力的工具与服务 | 保存片段及相关信息，按查询取得候选资料 |
| Milvus | 面向向量检索的数据系统 | 按数据、性能与部署需求评估 |
| Qdrant | 面向向量相似度检索的数据系统 | 按过滤、检索与部署需求评估 |
| FAISS | 高效相似度检索与聚类的库 | 为应用提供检索算法能力，不等于完整数据库服务 |

不要把 FAISS 限定为只能做实验；它也可以成为实际系统中的组件，但其他管理能力需要系统另行提供。也不能只按“数据超过某个固定条数”就决定必须换一种产品。

可核对：[pgvector](https://github.com/pgvector/pgvector)、[Chroma](https://docs.trychroma.com/docs/overview/introduction)、[Milvus](https://milvus.io/docs/overview.md)、[Qdrant](https://qdrant.tech/documentation/overview/)、[FAISS](https://github.com/facebookresearch/faiss)。

**神经网络** 是一类模型结构； **向量数据库 / 检索系统** 保存和查询表示； **知识图谱** 按实体与关系组织知识。它们可以配合，但不是同一个概念。

### 11.4 RAG：从导入到回答，分成两条流程

**RAG（Retrieval-Augmented Generation，检索增强生成）** 把资料检索与生成结合起来。可以用“先找相关材料，再根据材料组织回答”建立入门认识。[RAG 原始论文](https://arxiv.org/abs/2005.11401)

**第一条：准备资料。** 例如导入水杯说明书：

1. 保存原始文件，取得文字。
2. 把长文分成合适片段，这叫 **切分 / Chunking** 。
3. 为片段生成需要的检索表示，例如向量。
4. 保存片段、向量、来源和权限等信息。
5. 资料更新时，同步处理索引与旧片段。

**第二条：回答问题。** 例如询问能否放进洗碗机：

1. 接收顾客问题。
2. 按需要处理问题，检索可能相关的说明书片段。
3. 过滤无权访问或不适合使用的资料。
4. 将问题和合适片段交给模型。
5. 返回回答，并尽可能给出可核对的来源。

这是一种常见做法，不要求所有 RAG 都只用向量库。也可以采用关键词、向量或组合方式，即 **混合检索** 。

RAG 不等于训练或微调模型，也不等于模型逐个预测输出的全部过程。资料放入检索系统，不代表已经改变模型参数；模型检索到了内容，也仍可能误解或生成无依据说法。

**质量要检查哪里：** 文字是否识别正确、切分是否合适、资料是否更新、是否找到相关片段、回答能否对应到来源。不能只看“机器人能说话了”。

### 11.5 Function Calling、MCP 与 Agent

**Function Calling / Tool Calling（函数 / 工具调用）** 让模型按一定格式提出需要调用的工具与参数。随后由应用执行相应操作，把结果返回模型或用户。

例如用户问库存：模型提出调用“查询库存”，应用验证参数与权限，真正去查数据库，再返回数量。模型提出调用，不等于模型本身获得了任意执行权限。

**MCP（Model Context Protocol）** 是连接 AI 应用与外部工具、资源等能力的协议。可以减少每种工具都需要设计一套完全不同连接方式的问题。MCP 与模型的工具调用机制可以配合，但两者不是同一个东西。[MCP 官方介绍](https://modelcontextprotocol.io/docs/getting-started/intro)

**Agent（智能体）** 在不同产品中定义不同。入门可以理解为：围绕目标，结合模型、工具、状态与控制流程，执行多步任务的一类应用组织方式。

例如“查库存，满足条件再准备补货建议”比只回答一个问题多了过程安排。是否允许真正下单、修改数据，仍需应用中的明确权限和控制。

Agent 可以只使用工具与业务接口，并不一定需要向量数据库；普通网站也完全可以不加入 AI。

### 11.6 工作流、提示工程、RPA，以及课堂未展开的内容

**工作流 Workflow** 是把任务步骤、先后关系、条件与结果组织起来。例如“确认需求 → 分工实现 → 验证 → 汇总修改”。它可以由人、脚本或 AI 工具共同执行。

**提示工程 Prompt Engineering** 可以先理解为：把目标、上下文、限制、可用资料与验收方式讲清楚，并根据结果改进说明。不是只有寻找某一句固定的“万能提示词”。

**RPA（机器人流程自动化）** 通常用于自动执行重复操作，例如按规则操作业务软件和表单。它可以使用界面自动化，也可能与其他接口组合。它不等同于 Vue，也不等同于商品后端。

课程互动中提到若干 AI 开发工具及一个 Wiki 类方案，但录音不足以无歧义确认全部具体名称和版本。 **这节课没有完整演示那套工具链怎样搭建、怎样把任务交给各工具再验收。** 本笔记因此不把猜测的产品名或配置过程写成课堂事实。

如果用 Wiki 整理知识，可以先把它理解成一种知识内容组织方式；RAG 关注检索与生成流程，两者可能组合。不能仅凭“资料多或少”给出二选一的固定结论。

**本章自检：** 业务数据库记业务事实，文件存储留原文件，检索系统找资料，模型组织内容，工具执行动作，应用流程负责协调和约束。

## 12 两张课堂图怎样连起来看

### 12.1 多端产品管理图：先找同一份数据

第二张补充图中，管理页面、小程序和门户都与产品有关。 **门户** 可以先理解为面向相应使用者的信息与业务入口； **管理端** 面向有管理权限的人。

把交叉线简化后：

管理端调用管理接口，小程序或门户调用相应用户接口。它们可以共享产品业务逻辑和产品表，权限与返回字段则按各端的使用场景区分。

同一件商品，管理员能修改价格和上下架，顾客只看允许公开的信息。两组入口可能返回不同字段，也可能按同一套接口与权限设计处理。

屏幕大小会影响展示，但不能单独决定是否复制整个后端。共同规则尽量在适当位置共享，避免手机端与管理端各写一套，随后出现价格、权限不一致。

### 12.2 功能模块、功能点与接口粒度

**模块 Module** 是按业务职责组织的一组能力，例如商品管理。 **功能点** 更具体，例如新增、查询、修改、删除、上架、下架。

录音中的 **CRM** 指客户关系管理一类系统； **进销存** 围绕采购、销售、库存等业务；财务系统则处理相应账务业务。它们描述产品做什么，不是 Java、Python 之外的新语言。一个业务系统可以包含很多模块，不能只用名称或模块数量判断技术难度。

**粒度** 描述拆分粗细。“做商城”很粗，“实现一个有明确输入输出的商品查询接口”更细。但最细不一定最好，拆分应方便理解、分工、复用与验证。

图中“一个 Agent、一句话、一个模块”表达了一种任务拆分想法，不能理解成只说“做商品管理”就自动具备清楚需求。

更可检查的任务是：查询商品列表，字段有哪些，谁可以查询，每页多少，空列表怎样返回，失败怎样提示，怎样确认来自数据库。

### 12.3 服务器与 Docker 图：再看这些能力怎样运行

第一张图列出的 Nginx / Apache、JDK / Python、Tomcat、数据库、FFmpeg、Redis、Nacos、MinIO / FTP、Elasticsearch，以及自己的应用，是一组可能用到的能力。

把图读成三层更清楚：

服务器和操作系统提供运行条件；直接进程、容器与服务管理器组织程序的运行；入口服务、后端、数据库及按需增加的中间件在这些条件下启动和互相连接。

不是每一项都必须安装，也不是每个请求都依次经过清单里所有软件。例如保存商品价格，可以只涉及页面、后端和数据库；上传商品视频并生成封面，才可能增加文件存储和 FFmpeg。

### 12.4 把两张图真正连起来

多端图回答： **用户操作到哪一个业务接口，接口怎样使用数据？**

Docker 图回答： **这些接口与数据服务需要什么环境，在哪里运行，怎样互相连接？**

前者是业务与数据流程，后者是运行与部署条件。理解二者后，看到 AI 改了一个文件，就能继续追问：它改的是页面、接口规则、数据访问，还是启动配置？验证应沿哪条链路进行？

## 13 从需求到交付，怎样一步步做

### 13.1 先写需求，而不是先决定装多少软件

**需求** 描述谁要做什么、为什么做、结果应该怎样。先把商品练习写成可以检查的句子：

> 店员可以录入名称、价格和库存。名称不能为空，价格不能为负。保存后列表显示该商品，重新打开后仍能查到。普通顾客不能新增或修改商品。

**验收条件 Acceptance Criteria** 是判断功能完成的条件。例如输入空名称应提示错误，保存成功后重启服务仍能查询。

**选型** 是根据需求、已有环境和维护条件选择技术。课程强调选型意识，但不是要求新手一开始凭空比较所有框架。跟随一条适合的小路线，把原因解释清楚即可。

### 13.2 按一个可以验证的功能推进

| 阶段 | 实际动作 | 完成时能看到什么 |
| --- | --- | --- |
| 准备 | 看现有目录、说明、运行环境，选一个练习路线 | 能指出项目入口与启动方式 |
| 页面 | 做输入框、按钮、列表 | 点击后有正确界面行为，能解释暂时数据放哪 |
| 接口 | 后端接收查询或新增请求 | 不依靠业务页面也能试调并读懂响应 |
| 存储 | 接入一种数据库 | 记录真正保存，重启后仍可查 |
| 联调 | 页面调用真实后端 | 能在 Network 看到请求并验证数据变化 |
| 校验与权限 | 检查错误输入及不同身份 | 错误被拒绝，界面有合适提示 |
| 记录版本 | 检查差异、按需要记录修改 | 知道本次改了哪些文件与行为 |
| 部署 | 构建、配置、启动，连接目标数据 | 目标环境能完成同样流程 |
| 验收维护 | 外部访问、日志、备份与恢复检查 | 别人能用，失败有检查入口 |

这些工作会交错进行，例如 Git 从开始就能使用，安全也要随着功能加入。表格是理解先后依赖，不是把权限和验证全部留到最后。

### 13.3 四项安全基础，放到操作里理解

**第一项：密码哈希，区别于明文和普通加密。**

**明文** 是直接可读的原始密码。 **密码哈希** 用适合密码的算法与配置保存校验结果，登录时比较验证，不需要还原密码。 **盐 Salt** 帮助让相同密码也产生不同表示，成熟库通常会处理相关细节。

课件的 **bcrypt、Argon2** 属于密码哈希相关算法。新系统可以优先评估 Argon2id；已有系统还需按实际条件选择和配置成熟库。不能用普通快速哈希随便替代，也不能声称使用哈希后任何密码都绝对无法被猜解。[OWASP 密码存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

**第二项：密钥、.env 与 .gitignore。**

API Key、数据库密码等是真实凭据。`.env` 可以作为配置来源之一，但文件本身不是加密保险箱。 **`.gitignore`** 描述哪些未被追踪的文件不应被 Git 纳入管理，它不会自动清掉已经提交的敏感历史。

示例配置文件可以写占位内容，真实密钥由合适配置或密钥管理方式提供。已经泄漏的密钥，需要撤销或轮换，不能仅删除当前文件后继续使用。

**第三项：参数化 SQL。**

让用户输入作为“数据”传入查询，不把它直接拼成可以改变 SQL 结构的文本。 **SQL 注入** 就涉及把输入错误地解释为查询指令等问题。

MyBatis 常见参数写法是 **`#{...}`** ， **`${...}`** 是直接文本替换。课件里出现了重复符号，应以这里和官方文档中的准确写法核对；一些动态标识符需求也需要额外白名单等约束，不能机械认为任何位置都直接换占位符即可。[MyBatis 参数说明](https://mybatis.org/mybatis-3/sqlmap-xml.html)

**第四项：认证、授权、RBAC 与越权。**

- **认证 Authentication：** 确认“你是谁”，例如检查登录凭据。
- **授权 Authorization：** 判断“你现在能做什么”，例如是否可以修改这件商品。
- **RBAC（基于角色的访问控制）：** 根据角色配置一部分权限，例如店员与顾客。记录归属等规则可能还需要额外检查。
- **越权：** 访问了本不允许访问的数据或操作。登录成功不代表能查看所有订单；隐藏按钮也不能代替后端检查。

权限应在可信的服务端按请求和资源检查。使用成熟框架不代表这部分自动全对。[OWASP 授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

### 13.4 给 AI 的任务怎样写才容易验收

**不够具体：** “把所有工具用上，做一个高级商城。”

**更容易执行和检查：**

```text
我是零基础。请先检查现有项目与环境，再完成商品查询这一项功能。

显示字段：编号、名称、价格、上架状态。
数据来源：后端接口，后端查询当前项目使用的数据库。
范围：先只读，不加入订单、支付、缓存或向量检索。

请说明：
1. 前端、接口、业务处理、数据访问分别在哪个文件。
2. 查询请求和响应长什么样。
3. 在哪个目录运行哪条命令。
4. 成功时能看到什么，怎样确认不是写死的数据。
5. 错误去哪个日志或浏览器面板检查。

如果新增工具，请先解释它解决什么具体问题。
未运行的测试请明确说明，不要当成已通过。
```

这是一段补充的学习任务模板，不是课堂已经执行的命令。接下来再做新增、修改，每一步都保留清楚的验证结果。

### 13.5 看懂 AI 的工作报告

看到“已经修好了”，可以继续查看四种证据：修改差异、实际运行结果、请求响应、数据或日志。

**测试 Test** 是用特定输入与条件验证行为。自动测试只能覆盖它实际检查的情况；人工点过一次正常流程，也不能代表权限和异常输入都已验证。

**构建通过** 主要说明相应构建过程成功， **接口成功** 说明一次调用按条件完成， **端到端验证** 则尝试覆盖从用户入口到结果的一段完整流程。它们互相补充，不能随意替代。

## 14 出错怎样查，现在先学哪些

### 14.1 顺着同一条链路查，不乱改一堆工具

还是保存商品：先看操作是否触发，再看有没有请求，再看后端响应与日志，最后看数据库是否正确变化。

| 现象 | 第一轮检查 | 它还不能直接证明什么 |
| --- | --- | --- |
| 按钮没反应 | Console、按钮事件、前端校验 | 不能直接认定数据库坏了 |
| Network 没有对应请求 | 事件是否执行、请求代码、过滤条件 | 不代表后端已经接到操作 |
| 请求发到错误地址 | 接口配置、代理、当前环境 | 不需要先重装所有依赖 |
| 返回 404 | 方法、路径、路由、转发规则 | 不一定是整台服务器停止 |
| 返回 500 | 后端异常、日志、依赖状态 | 单靠状态码不能确定哪行错误 |
| 页面提示成功，刷新后消失 | 响应是否真实、是否写库、是否查同一数据库 | 成功提示不是持久化证据 |
| 容器内连不上数据库 | 地址、服务名、网络、端口、权限 | localhost 不一定指数据库所在环境 |
| 只有自己能打开 | 监听地址、网络、入口、防火墙、安全组 | 本地成功不等于外部可达 |
| 列表显示旧价格 | 主库结果、缓存、前端状态、环境 | 不是看到旧值就一定怪 Vue |

排错信息可以这样整理：我做了什么、期望什么、实际什么、请求地址与状态、相关日志、最近改了哪些文件。不要直接把含真实凭据的完整配置公开贴出。

### 14.2 当前最值得先亲手做的六个小结果

1. **一个页面。** 用编辑器打开文件，在浏览器看到标题、输入框、按钮，知道代码和显示怎么对应。
2. **一个交互。** 输入商品名，点击按钮显示到页面，明确这时是否只是内存数据。
3. **一个请求。** 在 Network 找到请求，读懂地址、参数、响应。
4. **一个后端接口。** 能启动和停止，能指出处理文件，能按项目说明试调。
5. **一次真实保存。** 写入数据库，重启后再查询确认。
6. **一次完整运行与检查。** 记录修改，验证正确和错误输入，知道日志与数据位置，再学习目标环境部署。

每项都以实际结果验收，不按“今天必须学会十个软件”的数量推进。遇到不懂的词，再回到对应章节。

### 14.3 工具按需要逐步加入

**第一轮就逐步练：** 文件与目录、编辑器与终端、HTML / CSS / JavaScript 基础、前后端、HTTP / JSON、一种后端路线、一种数据库、Git、日志、输入校验与权限。

**项目需要时动手：** Vue 与相关前端工具、Linux、Docker、接入配置和部署。若课程下一节已选 Vue 或 Java，沿课程路线走，不必为了这份笔记重新换栈。

**先认识用途，之后专题学习：** Redis、全文检索、对象存储、向量检索、RAG、微服务、复杂消息处理与 CI/CD。第一次新增一项能力时，就问它解决哪个明确问题、增加什么维护工作。

课堂最后说会带着准备环境。因此，上课前不用把图里所有软件一次装完。更合适的准备是：能找到项目目录，能看懂运行输出，能说出当前卡在哪个步骤。

### 14.4 怎样重新看这节录屏

如果从开头一直看仍容易迷糊，可以换这个顺序，时间是约略定位：

1. **82–95 分钟：** 产品管理图、JSON、Network、数据返回。先建立一次操作的整体感觉。
2. **10–16 分钟：** 浏览器页面、元素和样式。把页面对应到真实内容。
3. **39–50 分钟：** 模块、关系型数据、缓存、合同文件搜索。
4. **52–64 分钟：** Docker、运行环境、版本管理。此时再看“为什么有这么多服务”。
5. **72–80 分钟：** 向量与 AI，用第 11 章的准确概念对照。

先做一个小功能，再回看全景介绍，往往更容易把名称和实际操作关联起来。

## 15 完整性与容易误解的说法

### 15.1 本版怎样处理“完整”

本版重新对照 17 页课件、全程两遍机器转写和两张补充图，按教学主题与可确认术语梳理。既覆盖五层与四章主线，也补入了录音中的开发者工具、二开、分页轮询、多表查询、第三方调用等内容。

**完整复盘不等于逐字字幕。** 互动中的个人安排、重复语气和收费交流没有写进教学正文。画面采用全程抽样及关键节点核对，没有把它说成逐帧观看。

部分工具名与 Wiki 类方案在录音中难以确认，本版明示不确定，不用猜测补成“已经讲清楚的课程内容”。关于那套 AI 开发工具工作流，本节录屏没有提供完整搭建过程，不能从这份总览凭空还原。

另外，课件末页有“12 + 10 + 10 排课法”字样，但现有材料不足以确认其具体分配含义，未据此编排课程时数。

### 15.2 课堂口语需要校准的几个边界

| 容易误记的说法 | 本版使用的理解 |
| --- | --- |
| 名称都是可以点开的一套软件 | 先分语言、框架、库、协议、工具与服务 |
| Vue 用“Node.js 语法” | Vue 主要基于 JS / TS，Node.js 常运行开发工具 |
| H5、响应式布局、Vue 响应性是一回事 | 分别理解网页技术称呼、屏幕布局与状态驱动更新 |
| 手机 App 都只是浏览器套壳 | 原生、网页容器和跨端实现存在差别 |
| Boot 只适合小系统，Cloud 才适合大系统 | 结合需求、架构、测量和维护条件判断，二者也可配合 |
| MySQL 总要遍历全表，所以必须缓存 | 先看查询、索引、执行与数据情况 |
| MinIO 就是 FTP；文件绝不能进数据库 | 区分协议和产品，按文件访问与管理需求选择 |
| ES 是纯内存服务，IK 总是默认自带 | 区分索引与存储，中文分析方案要核对插件和版本 |
| Docker 包含独立小内核，打包后任何地方都能跑 | 容器共享内核等条件，仍需核对平台、配置与外部依赖 |
| Linux 没有桌面、没有病毒 | 服务器常用命令行，但仍有安全和维护要求 |
| Agent 都必须有向量库，RAG 就是逐字推理 | 分开理解模型生成、检索增强、工具与流程 |
| code 为 0 就是 HTTP 状态成功 | 区分业务返回约定和 HTTP 状态 |
| 推 Git 就等于部署，Git 能恢复所有数据 | 区分文件历史、构建、部署、配置与数据备份 |
| 有 AI 就可以不验证 | 仍需定位文件、运行服务、检查请求和数据 |

### 15.3 补充知识与课堂事实的界线
